## 1. 为什么需要保证长连接在线

### 1.1 长连接承担了什么

设备的下行通道不是平台主动拨号建立的，而是设备入网后自己建起来的：设备发起 TCP → 发 MQTT CONNECT 建会话 → SUBSCRIBE 下行 Topic → 之后平台才能往 `.../down/...` 投递。

> 在**本项目固件**里，这三个动作全部由 4G 模块（WH-LTE-7S1，内置 MQTT 客户端，`AT+MQTTMOD=1`）自己完成。MCU 侧进 NORMAL 前（State2，`gprs_AT.c`）只压 3 条查询 AT——`AT+ICCID?` / `AT+MQTTCID?` / `AT+CSQ?`，既不构造 CONNECT / SUBSCRIBE，也不感知 MQTT 会话是否真的建好——这正是后面必须用应用心跳回执来证明在线的原因。

这条链路一旦断掉，直接失效的能力有：

| 依赖 | 断链后果 |
| --- | --- |
| 控制命令下发（`down/service/invoke`） | 命令投递无接收方，控制中心显示「已发送」但设备收不到 |
| 设备在线状态 | 平台侧在线/离线失真，监控、告警、运维看板不可用 |
| 属性与事件上报 | 上报中断，趋势图出现空洞 |

因此「设备是否真的在线」是下行能力能否成立的前提条件。

### 1.2 4G 链路的四种典型失效

设备通过 4G 接入，链路中断是常态。四种失效的成因、现象与感知方：

| 场景 | 成因 | 现象 | 谁先感知 |
| --- | --- | --- | --- |
| 基站 / 核心网释放链路 | 运营商为复用无线与核心网资源，对长时间无数据交互的连接做 RRC 释放或承载拆除；部分 CGNAT / 防火墙对空闲 TCP 会话设有超时，超时后直接拆除 | 会话被单方面终止，设备上行随后报链路错误 | 通常**设备侧链路层**先感知；若释放后未触发任何本地状态变化，则**双方都不感知** |
| NAT 老化 | 运营商 NAT / CGNAT 为复用公网地址，给每条连接分配临时映射表项；长时间无报文经过时该表项被回收 | 设备发出的包仍能到达平台，但平台下行包到达 NAT 后因查不到映射而被直接丢弃 | **双方都不感知**：设备侧 Socket、平台侧 Socket 均未关闭，形成单向黑洞 |
| 基站切换 | 设备移动或信号变化时在小区间切换；极端情况下（PDP 上下文重建、跨制式回落）IP 也会变更 | 链路短暂中断或无线质量骤降，报文大量滞留；IP 变更时原 TCP 连接彻底失效 | 通常由**设备侧链路层**先感知；平台侧只能等 TCP 重传超时，这个过程可能长达数分钟 |
| 模块假连 | 4G 模块内部状态机异常或固件卡死，与基站的无线链路已中断，但串口侧仍接受 MCU 写入并回 `OK` | MCU 认为上报已正常发出，实际报文从未离站 | **双方都不感知**：设备应用层误以为发送成功，平台侧完全没有收到任何东西 |

### 1.3 失效的共同点

四种失效有一个共同点：**任何一端都无法仅凭本地状态判断链路是否真正可用。**

- TCP 半开连接在本机上会一直显示为 ESTABLISHED；
- 模块串口回包永远是 `OK`；
- 平台侧 Socket 只要没人关，就一直存在。

因此在线状态不能由「连接是否建立」或「发送动作是否返回成功」来证明，必须由**对端实际收到的报文**来证明。这是后面三层机制的设计出发点：

| 失效 | 由哪一层应对 |
| --- | --- |
| 基站 / 核心网释放链路、NAT 老化 | 第一层 MQTT 协议层保活：在链路上持续制造报文，避免空闲被回收 |
| 基站切换 | 第二层应用心跳 + 第三层回执：识别失联；两端各自重连与复位 |
| 模块假连 | 第三层心跳回执：上行能发、下行收不到的状态只能靠回执暴露 |

### 1.4 设计目标

本设计的目标**不是让连接永不中断**——4G 链路的中断无法在应用层消除。目标是两点：

1. **失联在数分钟内被识别**（平台侧最迟 390 秒判离线）；
2. **两端各自恢复**（平台侧状态自愈，设备侧硬复位模块重连）。

## 2. 如何保证：三层机制加两侧兜底

三层机制各管一件事，职责不重叠：

```text
第一层  MQTT 协议层保活   60s   PINGREQ / PINGRESP     维持 TCP 与 NAT 映射
            ↓
第二层  应用层心跳        120s  up/sys/heartbeat {}    设备证明自己活着
            ↓
第三层  心跳回执          跟随  down/request/reply {}  平台证明下行通道可用
            ↓
两侧兜底                                              平台扫离线 / 设备硬复位模块
```

| 层 | 周期 | 证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 协议层保活 | 60s | TCP 连接未被中间设备回收 | 设备是否活着 |
| 应用心跳 | 120s | 设备活着，上行通道可用 | 下行通道是否可用 |
| 心跳回执 | 跟随心跳，30s 节流 | 上行与下行双向通道均可用 | — |
| 平台兜底 | 360s 超时扫描 | 无上行即判离线 | 不能替代设备侧自愈 |
| 设备兜底 | 连续 3 次漏回执 | 上行能发但下行不通 | 不能区分平台故障与链路故障 |

> 注：表中 60s 是 4G 模块固件默认 Keep Alive 的**估计值**，本仓库未下发任何 Keep Alive 配置指令，无法在固件侧核实。120s、3 次、15min 是 `net_liveness.h` 的宏值，240s 由 `2 × NET_LIVENESS_INTERVAL_MS` 算出。

## 3. 第一层：MQTT 协议层保活

### 3.1 机制

设备在 MQTT CONNECT 报文里携带 Keep Alive 值（2 字节，单位秒），随后由 MQTT 客户端按该周期发送 PINGREQ（控制报文类型 12），服务端回 PINGRESP（类型 13）。设备侧按 60 秒估算，见 3.3 的说明。

作用是让 TCP 连接上持续有报文经过，使运营商 NAT / CGNAT 设备上的地址映射表项被不断刷新，也避免基站侧因长时间无数据而释放链路。它是连接层的心跳，**不参与平台的在线判定**。

### 3.2 CONNECT 不是心跳包，也不是物模型报文

MQTT 3.1.1 共定义 14 种控制报文，其中只有 **PUBLISH** 承载应用数据，其余均为协议自身的管理报文。本项目涉及的三种报文必须区分清楚：

| 报文 | 类型码 | 性质 | 频率 | 有无 Topic / 载荷 | 谁在处理 |
| --- | --- | --- | --- | --- | --- |
| CONNECT / CONNACK | 1 / 2 | 控制报文 | 建连时一次 | 无 Topic，载荷为固定字段 | 网关 `ValidateConnectionAsync` / `ClientConnectedAsync` |
| PINGREQ / PINGRESP | 12 / 13 | 控制报文 | 约每 60 秒（模块默认值，未核实） | 无 Topic、无载荷 | 两端都不在本仓库代码中，见 3.3 |
| PUBLISH | 3 | 应用报文 | 心跳每 120 秒，另有属性 / 事件 / 回执 | 有 Topic、有载荷 | 网关 `InterceptPublishAsync` + 接入侧 `IotAccessProcessor` |

CONNECT 是 TCP 三次握手之后、任何 PUBLISH 之前发出的第一个 MQTT 报文，用于建立 MQTT 会话，之后不再发送。其载荷是固定结构：协议名与版本、连接标志（含 CleanSession）、Keep Alive、ClientId，以及可选的用户名与密码。

本项目把身份放在 CONNECT 上：`username = deviceKey`，`password = deviceSecret`（本仓库 `uart3_at_sequence.c` 用 `AT+MQTTUSER=<deviceKey>` / `AT+MQTTPSW=<deviceSecret>` / `AT+MQTTCID=<deviceKey>` 写进模块），网关据此认证；认证通过才把会话放进 `_pendingSessions`：

CONNECT 里唯一与保活有关的就是那个 Keep Alive 字段——它只是**声明自己打算多久发一次 PINGREQ**，本身不是心跳。物模型的数据全部走 PUBLISH，包括本项目的应用心跳。

### 3.3 这层保活的代码在哪里

两端的 PINGREQ / PINGRESP 都由**现成实现**完成，本仓库没有该协议层处理逻辑的源码；设备端只有模块参数配置代码，见下表：

| 端 | 位置 | 说明 |
| --- | --- | --- |
| 平台（网关） | **MQTTnet 库内部** | 网关只注册了 `ValidatingConnectionAsync`、`ClientConnectedAsync`、`ClientDisconnectedAsync`、`InterceptingPublishAsync`、`InterceptingSubscriptionAsync` 五个回调。整个网关工程检索不到任何 PINGREQ / PINGRESP 的处理逻辑，保活由 MQTTnet 在协议层自动完成 |
| 设备 | **4G 模块固件内部**（本仓库可核实） | `uart3_at_sequence.c` 下发 `AT+MQTTMOD=1`（模块内置 MQTT 客户端）、`AT+MQTTSVR/MQTTUSER/MQTTPSW/MQTTCID`、8 个 `AT+MQTTPUBTP` 发布槽位与 5 个 `AT+MQTTSUBTP` 订阅槽位；这些参数只在 BLE 近场一键配置时写入模块并保存。全仓库检索不到任何 PINGREQ / PINGRESP 或 Keep Alive 配置指令，MCU 侧固件只往串口提交 `"槽位号,载荷"` 格式的应用层报文 |

因此 `DefaultKeepAliveSeconds`（默认 60，平台侧配置）当前未被消费、也未注入 MQTT 监听服务，**实际保活周期由模块固件 CONNECT 报文里那个 Keep Alive 值决定**。

> **更正（v2.1）**：本仓库既没有下发 Keep Alive 的 AT 指令，也没有读取模块该参数的代码，因此「设备侧 60 秒」无法从固件核实，只是按模块常见默认值给出的估计。要确认真实周期，只能在模块 AT 串口上抓 PINGREQ 间隔，或查 WH-LTE-7S1 的固件手册。这也是第 4.2 节流量估算里「协议层保活约 3.63 MB/台/月」的不确定来源。

## 4. 第二层：应用层心跳

### 4.1 机制

设备向 `up/sys/heartbeat` 发送一帧载荷为 `{}`（2 字节）的极简心跳，周期 120 秒。这是平台判定设备在线的**唯一证据**。

身份不放在载荷里，从 Topic 推导。平台侧把它补齐成标准信封后，复用既有 heartbeat 分支处理。

除心跳外，属性、事件、告警、服务回执、校时请求同样刷新设备的活跃时间，同样可证明在线。

### 4.2 报文格式

设备实际往串口写的是 4 字节帧（本仓库 `net_liveness.c` 的 `NET_LIVENESS_FRAME = "2,{}"`）：

```text
串口帧:  "2,{}"   → 首位 2 是模块发布主题槽位号，其后是载荷
                     共 4 字节，帧边界由模块 UARTFT 空闲切分，不需要 CRLF
                     入队后 300ms 即出队，不等串口回显、不等平台应答
```

模块把槽位号翻译成 MQTT 报文（槽位由 `uart3_at_sequence.c` 的 `AT+MQTTPUBTP` / `AT+MQTTSUBTP` 写入模块，发布/订阅 QoS 均为 0）：

上行：

```text
Topic:   iot/v1/{productKey}/{deviceKey}/up/sys/heartbeat   （模块发布槽位 2，QoS 0）
Payload: {}                                                  （2 字节）
```

下行：

```text
Topic:   iot/v1/{productKey}/{deviceKey}/down/request/reply （模块订阅槽位 5，QoS 0）
Payload: {}                                                  （2 字节）
```

单帧开销（按典型 pk/dk 长度估算的 MQTT 层字节数，不含 4 字节串口帧）：

| 项 | 字节 |
| --- | --- |
| 上行 PUBLISH | 62（固定头 4 + 主题 56 + 长度前缀 2 + 载荷 2） |
| 下行 PUBLISH | 64（固定头 4 + 主题 58 + 长度前缀 2 + 载荷 2） |
| 每周期合计 | 286（含 2 个 PUBLISH + 双向 TCP ACK 共 4×40 字节 TCP/IP 头） |

按 120 秒一帧、每月 30 天 = 21600 个周期，**6.18 MB/台/月**（700 台约 4.32 GB/月）。叠加设备原本约 60 秒的 MQTT 协议层保活（约 3.63 MB/台/月），蜂窝侧合计约 9.81 MB/台/月。

载荷压缩到 `{}` 之后，载荷与 MQTT 固定头只占 4%，主题占 40%，TCP/IP 头占 56%。

## 5. 第三层：心跳回执

### 5.1 机制

平台每收到一帧紧凑心跳，向 `down/request/reply` 回一帧 `{}`（2 字节），带 30 秒节流。

回执的作用是让设备确认「上行到达平台，且下行通道可用」。这一层专门用于识别**假连接**：会话仍然存活、上行也能发出，但下行已经收不到的状态。设备只判断「窗口内有没有收到下行」，因此回执不带 `id` 和时间戳。

### 5.2 实现

## 6. 两侧兜底

### 6.1 平台侧：在线判定与离线扫描

**判定口径**：在线只由**设备自身报文**刷新。网关代发的帧不计入设备活跃，`LastSeenTime` 只在设备上报（紧凑心跳、属性、事件、服务回执、校时请求）走上行链路进来时更新。

`DeviceOfflineDetectionHostedService` 是 admin-api 里的后台扫描任务。它不看 TCP 是否还连着，只看状态快照里的 `LastSeenTime`。

`ScanOnceAsync` 每次从 `iot_device_status_snapshot` 里挑还标着在线、并且 `LastSeenTime` 早于「现在减去 `OfflineTimeoutSeconds`」的设备，按 `LastSeenTime` 从旧到新取，一次最多 `BatchSize` 条。

对挑出来的每一台，再读一遍快照和设备档案，仍然在线则：

- 快照改为离线，版本加 1，简要 JSON 里写上 `heartbeat_timeout`、超时秒数、最后活跃时间和本次离线时间；
- 设备档案记下 `LastOfflineTime`；运行状态不是停用时改成离线，已停用的不改；
- MongoDB 影子的 `OnlineStatus` 写成 `offline`，`LastMessageType` 写成 `offline_timeout`；
- `WriteInfluxStatus` 为 true 时再写一条离线状态时序。

配置：

```json:196:203:Admin.NET-v2/Admin.NET/Admin.NET.Application/Configuration/Iot.json
  "IotDeviceOfflineDetection": {
    "Enabled": true,
    "InitialDelaySeconds": 20,
    "ScanIntervalSeconds": 30,
    "OfflineTimeoutSeconds": 360,
    "BatchSize": 500,
    "WriteInfluxStatus": true
  },
```

默认 360 秒配合设备 120 秒心跳，容忍连续 3 次丢失。一台断电设备最迟在 360 秒 + 一次扫描间隔内被判离线。

### 6.2 平台侧：状态分叉对账

`iot_device` 与 `iot_device_status_snapshot` 由两条独立写后置队列维护。`DeviceStatusReconcileHostedService` 修复两个方向的分叉：

| 方向 | 条件 | 动作 |
| --- | --- | --- |
| 一 | 快照已离线、且 `LastSeenTime` ≥ 档案 `LastOnlineTime`，但档案仍在线/告警 | 档案改离线，补 `LastOfflineTime` |
| 二 | 快照在线且 `LastSeenTime` 在新鲜窗口内，但档案离线/未知 | 档案补写在线，补 `LastOnlineTime` |

修正后按 `InvalidateAccessCache` 决定是否清除接入侧缓存。两处修正均打 `LogWarning`，便于反向排查写后置队列。

### 6.3 设备侧：链路存活自愈

**驱动点**：`Gprs_Process()`（`gprs_JSON.c` L357–L398）的第 4.1 步 `NetLiveness_Process()`，位于 `Parse_Process()` / `gprs_state_machine()` 之后、`UartTx_Queue_Process()` 之前。由 `gprs_is_ready()`（`gprs_AT.c`，`gprs_state == GPRS_STATE_NORMAL`，状态号 4）把门；非 NORMAL 时本函数每轮只调用 `NetLiveness_ResetState()` 后返回，而同一总闸会让**所有上行（含心跳）静默丢弃、不缓存不重发**。

主流程（`net_liveness.c`）：

1. **首帧有门槛**：每次进 NORMAL 都要重新等 `sys.timeSync ok`；未解锁时 `liveness_tick()` 直接返回，不发心跳、不计 `miss`、不刷新周期起点。解锁后才发第一帧，之后每 `NET_LIVENESS_INTERVAL_MS`（120 秒）发一帧 `"2,{}"`。
2. 发帧后置 `s_pending = 1`；到下个周期发新帧前若仍在途，则 `s_miss++` 并重发。
3. 收到 `{}` 回执（`NetLiveness_IsAck()`：是对象且数组长度为 0）→ `NetLiveness_OnAck()` 清 `s_miss`、记 `s_last_ack_ms`，且**只在 `s_pending == 1` 时生效**。该分支在 `Parse_Process()` 中先于严格信封校验；同时清掉残留 `id` 并调用 `Gprs_ClockSync_OnDownlinkOk()`，把回执当作「双向通道可用」的证据交给对时逻辑（`gprs_JSON.c` L469–L479）。
4. `s_miss >= NET_LIVENESS_MISS_THRESHOLD`（3，约 6 分钟）**且** `GM4G_ResetAllowed(NET_LIVENESS_L1_MIN_INTERVAL_MS)`（15 分钟）→ `s_miss = 0`、清发送队列、置 `s_pending = 0`、`GM4G_Reset()` 硬复位 4G 模块；可无限次重复。

**两条触发路径，一个动作**：

| 触发路径 | 条件 | 动作 |
| --- | --- | --- |
| 稳态漏回执 | `s_miss >= 3`（约 6 分钟）且 15 分钟节流允许 | 清发送队列 + 放弃在途帧 + `GM4G_Reset()` |
| 等待校时期间卡死 | `s_ts_fail >= NET_LIVENESS_TSFAIL_THRESHOLD`（3）且节流允许 | 同上，另重置对时快节奏 |

动作只有一种：模块按**自己已保存的 MQTT 参数**重连重订阅。自动流程不校验、不下发、不保存任何模块配置，也不重启 MCU；模块参数重配置只保留在 BLE 近场一键配置（`sbf20_app` → `uart3_at_sequence`）这条人工路径上。

**复位节流为共享时间线**：

- `s_last_reset_ms` / `s_reset_ever` 由 `4G.c` 的 `GM4G_Reset()` 统一记录，用 `GM4G_ResetAllowed()` / `GM4G_ResetWaitRemainingMs()` 判定；`GM4G_Init()` 的上电 RST 脉冲不计入。
- 于是状态机离线硬复位（`gprs_AT.c`，≥5 分钟）、探活/校时自愈（≥15 分钟）、BLE 重配置后复位**共用同一条时间线**，任一路径刚复位过，其他路径都会看到，不会再出现「状态机刚复位、应用层 90 秒后又复位」。
- `liveness_recover()` 在复位前**显式 `s_miss = 0`**；`NetLiveness_ResetState()`（每次进非 NORMAL 都调用）只重置 `s_pending`、`s_ever_sent`、`s_wait_timesync = 1`、等待日志与快节奏标志，**保留** `s_miss`、`s_last_ack_ms`、`s_ever_acked`——链路闪断不清失联计数，避免「复位 → 闪断清零 → 又立刻复位」的复位风暴。
- 首次复位不受间隔限制（约 6 分钟即动作），之后稳态约每 15 分钟一次。复位后要重新走「3 条 AT → 校时 → 首帧心跳」，**等待校时期间不发心跳**，因此「心跳探活始终每 120 秒一帧」并不成立。
- 复位被节流挡住时，等待校时的节奏由 5 秒退回 60 秒（`NetLiveness_IsTimeSyncFast()` 返回 0），并只打印一次 `reset throttled` 提示，避免长时间平台故障下高频探测。

配套能力：

- **首帧心跳等校时成功**：每次进 NORMAL 由 `Gprs_PeriodicPush_Process()` 先热身 2 秒（等模块 MQTT 会话/订阅建好；模块侧 `AT+CACHEN=OFF` 关闭上行缓存、属可选指令，发早了这帧会被直接丢弃），再发 `sys.timeSync`；`reply_cjson_clock()` 解析 `body.output.serverTime`、写入 DS1302 后调用 `NetLiveness_OnTimeSyncOk()` 解锁首帧。等待期对时节奏压到 5 秒（常态为 15/30/60 秒退避），一轮 3 次尝试约 15 秒即累计 3 次失败并触发复位判断（另加起重试一轮的 5 秒间隔）。等不到 `code=0` 就一直不发心跳，因此该产品物模型必须启用 `sys.timeSync`——但须同时注意第 8 章的 F1 缺陷。
- **LCD 三态在线指示**：`在`＝模块在线且平台已确认；`未`＝模块已注网但平台尚未确认；`离`＝模块未注网（`gprsonlineflag` / LINKA 低）。数据源 `DispalyPara.c` 的 `DisplayState()` → `NetLiveness_IsServerConfirmed()`：要求 `s_ever_acked` 为真且距上次回执 < `2 × NET_LIVENESS_INTERVAL_MS`（240 秒）。
- **EEPROM 凭据保护**：`24cxx.h` 的 `EE_ADDR = 250`；`AT24CXX_Check()` 在标记丢失时读 `pk[0]` 与 `gate_maxheight` 判断数据区是否已初始化，已有内容只补标记、不播默认值；`reg.c` 的 `mqtt_eeprom_write_str()` 在首字节非 `0x00`/`0xFF` 时直接跳过，只写空白槽。

## 7. 时间线

> 前提：设备已拿到 `sys.timeSync ok`、心跳进入 120 秒稳态。若失联发生在「等首帧心跳」阶段，节奏由 5 秒对时快重试与 15 分钟复位节流决定，不走下表。

| 时刻 | 平台侧 | 设备侧 |
| --- | --- | --- |
| T+0 | — | 链路中断（基站释放 / NAT 老化 / 基站切换 / 模块假连） |
| T+120s | 未收到心跳，`LastSeenTime` 停止更新 | 下一帧心跳发出时上一帧仍在途 → `miss=1` |
| T+240s | 同上 | `miss=2` |
| T+360s | `LastSeenTime` 超过 360 秒阈值，离线扫描命中 | `miss=3` → 同一轮 `liveness_recover()` 判定复位 |
| T+360s（即 T+6min） | — | 硬复位 4G 模块（首次不受 15 分钟节流限制），清发送队列、放弃在途帧 |
| T+360~390s | 最迟一次扫描间隔（30s）内完成离线落库 | 模块重新注网 → 3 条 AT → 校时；拿到 `code=0` 前不发心跳 |
| 恢复后 | 收到复位后的**首帧心跳**才由离线翻回在线 | 收到 `{}` 回执，`s_miss` 清零，LCD 由「未」转「在」 |

**两端节奏几乎同步，不要误读成一大段窗口**：平台 360 秒判离线、设备 360 秒触发复位，设备侧最多只比平台早一次扫描间隔（约 30 秒）。真正拉长时间的是复位后的重新上线过程（注网 + 3 条 AT + 2 秒热身 + 校时成功），这段时间平台保持离线、设备不发心跳。现场看到「串口在重启、平台一直离线」是预期行为，而不是自愈失败。

## 8. 边界：本设计没有保证的部分

| 项 | 说明 |
| --- | --- |
| 心跳上行的可靠性 | 心跳走 QoS 0（省流量），单帧可能丢失，靠「连续 3 次漏回执」容错 |
| 回执的迟到识别 | 回执不带 `id`，无法识别迟到或重复回执，设备只判断窗口内是否收到 |
| 回执下发失败 | catch 中只记日志，设备侧按漏收处理并在下个周期重发心跳 |
| 断链瞬间的即时感知 | 平台侧最迟 390 秒判离线，不保证秒级感知；只有设备主动断开发 DISCONNECT 时网关才立即代发 offline |
| 平台故障与链路故障的区分 | 设备侧只能观察到「收不到回执」，无法区分是链路问题还是平台问题 |

**设备侧另有三条已由本仓库源码确认的边界**（详见 [Gprs_Process_explained.md](./Gprs_Process_explained.md) 第 5 章）：

| 项 | 说明 |
| --- | --- |
| **F1（高）`timeSync` 业务失败会锁死心跳** | `reply_cjson_clock()` 在 `body.code != 0` 时直接 `return`：既不调用 `NetLiveness_OnTimeSyncOk()` 解锁首帧，也不调用 `NetLiveness_OnTimeSyncFail()` 累计失败。于是 `s_wait_timesync` 恒为 1、`s_miss` 恒为 0，等待期自愈也不触发，设备要等下一次 24h 对时周期才可能恢复。期间平台收不到心跳会判离线，属性上报仍带着未校准的错误时间戳。**所以「产品物模型必须启用 sys.timeSync」之外还有个前提：平台必须始终返回 `code=0`** |
| **F9（低）回执判据只认空对象** | `NetLiveness_IsAck()` 只检查「是对象且大小为 0」，任何恰好为 `{}` 的下行都可能在 `s_pending == 1` 时被当成心跳确认。靠「实际下行几乎不存在空对象」与 `OnAck()` 要求 `s_pending` 降低风险，但没有强校验 |
| **非 NORMAL 态上行静默丢弃** | `gprs_is_ready()` 为假时 `UartTx_Push_JSON()` 直接返回 0，事件、属性、心跳全部丢弃，不缓存、不重发、不打印。掉线期间发生的一切在云端永久缺失，现场只能靠 `[GPRS] State*` 日志反推 |

## 10. 怎么核对

| 看哪里 | 来源 | 能确认什么 |
| --- | --- | --- |
| 设备串口 `[LIVE] heartbeat ack ok (miss=N)` | 本仓库 `net_liveness.c` | 每 120 秒一条，正常 `N=0`；心跳确实被平台确认 |
| 设备串口 `[LIVE] first heartbeat held: waiting sys.timeSync ok`、`[LIVE] timeSync stuck 3 times -> hard reset` | 同上 | 是否卡在等校时（可能命中第 8 章 F1）／等待期自愈是否触发 |

| 网关 / 诊断日志 | 平台侧 | 每 120 秒一帧 `up/sys/heartbeat`（2 字节）与一帧 `down/request/reply` 成对出现 |
| 设备快照 `LastHeartbeatTime`、在线状态 | 平台侧 | 心跳是否在更新；该字段不动即代表设备已失联 |
| 网关 `/metrics` 的 `CurrentConnections` 与平台「在线设备数」 | 平台侧 | 两者对不上即存在「会话还在但设备已不心跳」的假连接 |
| `ScanOnceAsync` 日志 | 平台侧 | 心跳超时判离线的生效情况 |

> 平台侧四项本工作区无法核对；**设备侧三项可直接用串口日志验证**，是排查假连接时最该先看的证据。
