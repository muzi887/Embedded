# 嵌入式节点通讯协议应用规范(基于SL651 ASCII模式)

**文档属性**

- **分类**: IIoT / 协议文档 / 方案设计
    
- **版本**: V4.0 (ASCII字符编码版)
    
- **适用对象**：嵌入式 C 语言开发工程师、系统测试工程师、项目验收与平台对接人员
    
- **更新日期**: 2026-04-22
    

## 1. 概述

本规范定义了水文监测节点中**协议转换网关**与中心站（云端服务器）之间的上行数据通讯标准。网关下行采用 Modbus 等协议采集底层异构设备数据，上行严格遵照国家水文通讯规约标准《SL651-2014》的 **ASCII 字符编码传输模式**（规约 6.4 节）进行格式转换与动态封包。

- **设备定位**：多协议转 SL651 网关（本机主要支持 M1 模式/无回答测试报发报）。
    
- **核心机制**：采用 **“配置驱动 + 动态格式化”** 架构。系统通过解析下发的 JSON 配置文件，动态读取传感器数据源（Source），依据配置规则（Format）将其格式化为标准 ASCII 字符串，并在数据间自动插入空格分隔符，完成最终报文的拼装。
    

## 2. 链路层与传输模式配置

### 2.1 基础物理链路

- **通讯接口**：RS-485 / 4G DTU 透传 / TCP直连
    
- **波特率**：9600 bps (默认)
    
- **数据位**：8位 / **停止位**：1位 / **校验位**：无 (None)
    

### 2.2 链路传输模式及状态机映射 (核心规则)

根据《SL651-2014》第 6.3.1 节规定，网关需支持四种核心链路传输模式。网关底层通讯状态机需严格读取 JSON 配置文件中 `meta_config.protocol_mode` 的值，并据此执行不同的超时与重发逻辑：

|**模式代号 (JSON 配置项)**|**模式种类**|**适用工作制式**|**网关通讯状态机执行逻辑 (MCU Engine Logic)**|
|---|---|---|---|
|**M1**|发送/无回答|自报式|**(本机默认模式)**。遥测站为通信发起端，发出报文后，中心站不需响应。单片机执行逻辑：发送完毕后立即退出通讯状态（休眠或关闭 4G 模块），无超时等待。上行报文结束符强制为 **ETX**。|
|**M2**|发送/确认|自报式|遥测站为通信发起端。单片机执行逻辑：发出报文后，必须启动内部接收定时器等待中心站下发“确认”帧。若超时未收到，启动重发机制（**最多重发 2 次**）。后续有报文时结束符为 **ETB**，最后一帧结束符为 **ETX**。|
|**M3**|多包发送/确认|自报式|遥测站为通信发起端，连续发出多包数据。单片机执行逻辑：根据中心站返回的错包序号列表进行针对性重发（最多重发 2 次）。单片机需在 RAM 中维护发报队列与序号状态机。|
|**M4**|查询/响应|查询应答式|**中心站为通信发起端**。单片机执行逻辑：网关平时处于事件监听（Receive）状态，接收并校验中心站的请求报文正确后，立即依据请求类型组包并发送响应帧。|

> **开发注记**：配置软件在生成 `message.json` 时，必须确保 `meta_config.protocol_mode` 的值（M1~M4）与 `tail` 段落中 `message_end`（结束符 ETB/ETX）的逻辑匹配。运行软件（单片机）不负责校验配置冲突，仅严格按照 `protocol_mode` 的指令切换网络收发线程的工作模式。

### 2.3 报文任务调度与触发机制 

本网关支持多类型报文并发运行。配置软件下发的 `message.json` 本质上是一个 **“任务调度数组”**。

- 在 `meta_config` 中需声明 `trigger` 属性，支持 `timer`（定时触发）与 `manual`（事件/人工触发）两种模式。
    
- 运行软件（单片机）在初始化阶段遍历该数组，依靠 `trigger` 引擎为不同报文分配独立的时间轮（Timer Wheel）或中断监听。当触发条件达成时，仅提取当前任务对应的 `segments` 执行动态组包逻辑，从而实现多报文任务的互不干扰与高度内聚。

## 3. 报文帧格式结构 (基于 ASCII 字符编码)

上行通讯采用 **HEX 控制字符与 ASCII 可视字符混合** 的编码方式。为实现“配置驱动状态机”，最新的 JSON 配置模型升级为 **“配置元数据 (`meta_config`) + 报文段落 (`segments`)”** 的复合结构：

- **`meta_config` (元数据层)**：包含 `protocol_mode` (链路传输模式，如 M1) 和 `message_type` (报文类型)。该层数据不参与实际报文拼装，而是用于直接控制单片机的通讯状态机（如：M1 模式下发送完毕后直接休眠，不启动等待 ACK 的接收计时器）。
    
- **`segments` (段落层)**：严格划分为 `header`（报头）、`payload`（正文）、`tail`（报尾）三段。每个段落新增了 **段落级 `length`** 字段，用于单片机（MCU）在解析前进行安全的内存预分配与缓冲区防溢出校验。由于 `payload` 会根据传感器状态动态跳过无效数据，其 `length` 设为 `0`，总长度由程序运行时实时计算。
    

**核心动态计算规则：**

- 对于不可见的控制字符（如 SOH, STX, ETX），JSON 中配置为 `format: "HEX_CTRL"`，单片机解析时直接作为 1 字节十六进制原样发送，不作字符串转换。
    
- **报文长度与校验码不能写死**：在 JSON 中其 `value` 仅作占位（如 `0000`），单片机需根据对应的 `source` 指令（`sys_calc_length` 和 `sys_calc_crc`）在内存拼包阶段进行**实时动态计算与回填**。

单帧报文（以 M1 模式测试报为例）结构如下：

| **序号** | **所属段**     | **字段名称**           | **字节/字符数** | **标识符/取值说明 (按 JSON 配置逻辑)**                                                  |
| ------ | ----------- | ------------------ | ---------- | --------------------------------------------------------------------------- |
| 1      | **header**  | **帧起始符 (SOH)**     | 1 Byte     | 固定 HEX: `01` (`format: "HEX_CTRL"`)                                         |
| 2      | **header**  | **中心站/遥测站地址/密码**   | N Char     | 均为 ASCII 字符串                                                                |
| 3      | **header**  | **功能码 (Function)** | 2 Char     | `30`为测试报，`32`为定时报                                                           |
| 4      | **header**  | **上行标识及长度**        | 4 Char     | **动态生成** (`source: sys_calc_length`)。高位0表示上行，后3位为拼接完 payload 后的实际字节数转 ASCII |
| 5      | **header**  | **正文起始符 (STX)**    | 1 Byte     | 固定 HEX: `02` (`format: "HEX_CTRL"`)                                         |
| 6      | **payload** | **流水号 **           | 4 Char     | 无前导标识符，尾部**无空格分隔符**                                                         |
| 7      | **payload** | **发报时间 **          | 12 Char    | 无前导标识符，尾部**无空格分隔符**                                                         |
| 8      | **payload** | **遥测站地址 ~~(选编)~~** | N Char     | 标识符 `ST`，尾部带固定空格。通常在 M3 模式多包发送或特定测试报中按需编入。                                  |
| 9      | **payload** | **遥测站分类码 (选编)**    | 1 Char     | 无前导标识符，数据内容(如 `H`)后尾部带固定空格。根据功能码定义选编。                                       |
| 10     | **payload** | **观测时间 (选编)**      | 10 Char    | 标识符 `TT`，尾部带固定空格。                                                           |
| 11     | **payload** | **业务要素组 (传感器数据)**  | N Char     | 降水、水位等参数。统一按照“标识符 + 固定空格 + 格式化数据 + 尾部空格”拼接。                                 |
| 12     | **tail**    | **报文结束符 (ETX)**    | 1 Byte     | 固定 HEX: `03` (`format: "HEX_CTRL"`)                                         |
| 13     | **tail**    | **校验码 (CRC)**      | 4 Char     | **动态生成** (`source: sys_calc_crc`)。对全包计算 CRC-16 后转为 4 位 ASCII                |

## 3.5 内部交互接口（本地数据池 Data Pool）

为实现采集与上报解耦，嵌入式程序内部维护一个全局结构体。传感器任务更新该结构体，SL651 封包任务根据 JSON 的 `source` 字段来这里取值。

```C
typedef struct {
    float current_rainfall; // 当前降水量 (对应 JSON source)
    float voltage;          // 电源电压 (对应 JSON source)
    // ... 其他待扩展数据
    
    uint16_t status_flag;   // 数据更新位图 (用于动态组包跳过无效数据)
} GlobalDataPool_t;
```

## 4. 数据正文与标准 JSON 节点模型 (Payload Mapping)

本节定义网关正文（Payload）的转换规则。为了实现“配置驱动单片机”的目标，正文中的所有数据（无论流水号、时间还是传感器数值）必须在 JSON 配置中遵循 **“大一统”的标准节点模型**。

### 4.1 SL651 要素节点标准模型定义

配置工具下发给网关的 `segments` 数组中，针对 `name` 为 `payload` 的段落，其内部 `fields` 数组中的每一个对象，都包含以下完整属性，单片机按此规则统一执行：

```JSON
{
  "name": "current_rainfall",      // 内部唯一英文键，PC和MCU靠它进行变量绑定
  "desc": "当前降水量",            // 中文描述，供配置UI使用
  "identifier": "PJ",              // 【关键】规约标识符(如ST, TT, PJ)。若无标识符(如流水号)则为空 ""
  "value": "00005",                // 静态测试值或占位符
  "source": "modbus_reg_0",        // 【关键】数据源。指示单片机去哪个底层接口取真实数据
  "format": "N(5,1)",              // 格式化规则，指导单片机如何进行 sprintf 转换
  "type": "float",                 // 内存数据类型 (int, float, string, datetime)
  "length": 5,                     // 数据转换后的字符长度
  "unit": "mm",                    // 物理单位（仅显示）
  "separator": " "                 // 【关键】尾部分隔符。标识符与要素之间、要素与要素之间必须为空格 " "，仅流水号与发报时间后为无空格 ""
}
```

### 4.2 单片机拼接执行逻辑 (MCU Engine Logic)

单片机在处理 `payload` 数组时，采用无差别的循环遍历拼接机制：

1. **查验状态位 (Status Flag)**：读取 `source` 绑定的本地数据池，若该项传感器失效或未更新，直接跳过当前节点，进入下一循环（触发动态长度改变）。
    
2. **拼接标识符 (Identifier)**：若节点的 `identifier` 不为空（如 `PJ`），则将标识符写入 Buffer，并**紧跟一个固定空格**。
    
3. **获取与格式化数据 (Data & Format)**：
    
    - 提取 `source` 对应的实时数据。
        
    - 依据 `format` 规则（如 `N(5,1)` 表示转为5位整数，隐含1位小数）将其转换为定长 ASCII 字符串并写入 Buffer。
        
4. **追加分隔符 (Separator)**：将 `separator` 字段的值（空格或空字符）追加到当前要素末尾。

### 4.3 动态格式化指令解析：N(D, d) 规则

为保证上行报文完全符合 SL651 规约，网关引擎需内置针对 `format` 字段中 `N(D, d)` 格式的解析与转换函数。传感器采集到的物理量（浮点数）必须通过此规则转化为定长 ASCII 字符串，且**不包含小数点**。

- **通用解析逻辑**：
	
	- 对于标识为 `N(D, d)` 的要素，设实际采集的浮点数值为 `V`：
	
	- **放大倍数**：计算整数值 `Val_Int = (int)(V * 10^d)`
	
	- **格式转换**：使用格式化函数（如 `%0*d`），将 `Val_Int` 转换为总宽度为 `D` 的字符串，不足部分左侧补 `0`。

- **示例 1：降水量 `N(5,1)`**
	
	- 含义：总长度 5 字符，包含 1 位小数。
	
	- 转换过程：底层采集到 `12.5 mm` $\rightarrow$ 乘以 $10^1$ 变为 `125` $\rightarrow$ 补零至 5 位变为 `"00125"`。
	
	- 最终拼装：`PJ 00125 ` 

- **示例 2：电源电压 `N(4,2)`**
	
	- 含义：总长度 4 字符，包含 2 位小数。
	
	- 转换过程：底层采集到 `10.91 V` $\rightarrow$ 乘以 $10^2$ 变为 `1091` $\rightarrow$ 长度已为 4 位变为 `"1091"`。
	
	- 最终拼装：`VT 1091 `
        

### 4.4 异构时间域组包机制 (多时间戳处理)

在真实的工业物联网与水文监测现场，受限于传感器的预热机制或总线轮询延迟，不同要素（如降水量与水位）的实际采集时间往往存在物理差异（即异步采集）。为解决底层时间的“碎片化”与上行报文“同步性”之间的矛盾，本网关结合《SL651-2014》规约 6.6.2.8(e) 规定，采用 **“时间作用域依赖”与“配置解耦”** 的机制进行组包。

**1. 规约层的时间作用域 (`TT` Scope)**

根据规约要求，观测时间组（标识符 `TT`）并非与单个要素强制绑定，而是呈现“向后统领”的作用域特性。解析器遇到 `TT` 后，其后紧跟的所有要素数据均默认归属该时间，直至遇到下一个新的 `TT` 标识符。

**2. 标准常态化组包 (同源时间)**

当网关执行定时报或测试报，且各传感器数据属于同一轮询周期（时间误差可忽略）时，配置软件在 JSON `payload` 数组的最前端仅放置一个 `observe_time` (`TT`) 节点，后接所有业务要素。单片机拼装结果为：

`... TT 1707181000 PJ 00005 Z 012500 VT 1091 ...` _(全局共享一个观测时间)_

**3. 异构异步组包机制 (动态插入 TT)**

若业务要求将采样频率完全不同（或时间差异巨大）的要素合并于同一帧报文中发送，**单片机（MCU）的底层 C 语言解析与组包代码（`for` 循环拼接引擎）无需作任何修改。** 系统通过 **PC 端配置软件** 承担逻辑路由的职责：

- PC 软件在生成 `message.json` 时，若判定后续要素的时间源与当前时间源不同，将自动在对应要素的 JSON 对象前，**插入一个新的观测时间节点**，并绑定对应内存区的时间戳（`source`）。
    
- 单片机严格按照 JSON 数组顺序无差别遍历拼接，自然生成的报文形态如下：
    
    `... TT 1707181000 Z 012500 TT 1707181005 PJ 00005 ...`
    
- **解析结果**：中心站依据规约标准，自动将 `10:00` 赋予水位，将 `10:05` 赋予降水。从而实现硬件设备异步采集到规约合法报文的完美闭环。

## 5. 常见功能码定义

基于网关的自报与响应场景，依据《SL651-2014》附录 B.1 规范，核心功能码（即 JSON 中的两字符 ASCII 字符串）定义如下：

|**功能码**|**应用功能描述**|**说明**|
|---|---|---|
|`2F`|链路维持报|遥测站定时向中心站发送链路维持信息|
|`30`|测试报|报送实时数据|
|`31`|均匀时段水文信息报|报送等时间间隔数据|
|`32`|遥测站定时报|报送由时间触发的实时数据|
|`33`|遥测站加报报|报送由时间或事件触发的加报实时数据|
|`34`|遥测站小时报|报送以小时为基本单位的历史数据和实时数据|
|`37`~`3A`|中心站查询遥测站数据|包含中心站查询实时数据、时段数据、指定要素数据等|
|`41`/`43`|中心站读取配置表|中心站读取遥测站基本配置表或运行参数配置表|

## 6. 通讯示例分析 (报文级抓包解析)

**【场景与状态机初始化】**：网关加载 JSON 配置，准备发报。

- **读取 Meta 状态机配置**：MCU 提取 `meta_config.protocol_mode` 为 `"M1"`，`message_type` 为 `"测试报"`。通信引擎自动进入“发送后不启动接收计时器”的单向发报状态，并锁定报头中的功能码字段应为 `30`。
    
- **执行内存预分配**：MCU 扫描 `segments` 数组的段落 `length`，得知报头固定 24 字节，报尾固定 5 字节，正文长度动态计算，从而安全地在 RAM 中初始化发送 Buffer。
    
- **数据区状态**：
    - 站号：`0012341234`
    - 流水号：`0019`
    - 降水量采集值：`0.5 mm` -> format `N(5,1)` -> `"00005"`
    - 瞬时水位采集值：`12.500 m` -> format `N(7,3)` -> `"0125000"` 
    - 电压采集值：`10.91 V` -> format `N(4,2)` -> `"1091"`

**单片机最终生成的报文流如下（直观展示）：**

```Plaintext
[0x01]06001234123404D2300049[0x02]0019170718111204ST 0012341234 H TT 1707181112 PJ 00005 Z 0125000 VT 1091 [0x03]ABCD
```

_(注：为方便阅读，控制字符用 [] 标注，实际传输为单字节 HEX)_

**【报文逐段拆解与 JSON 节点对应】**：

1. **报头段 (Header)**:
    
    - `[0x01]` : 帧起始符 (JSON 中 `format: "HEX_CTRL"`)
        
    - `06` : 中心站地址
        
    - `0012341234` : 遥测站地址
        
    - `04D2` : 密码
        
    - `30` : 测试报功能码
        
    - `0049` : **动态长度** (正文拼装完毕后，由 `sys_calc_length` 动态计算。当前正文共计 73 字节，十进制 73 转十六进制即为 0x49)
        
    - `[0x02]` : 正文起始符 (JSON 中 `format: "HEX_CTRL"`)
        
2. **数据正文段 (Payload) - 严格映射 JSON 节点拼接逻辑**: _(拼接公式：标识符 + 固定空格(若标识符非空) + 数据值 + 尾部分隔符)_
    
    - `0019` : 【流水号节点】无标识符，无尾部空格。
        
    - `170718111204` : 【发报时间节点】无标识符，无尾部空格。
        
    - `ST 0012341234` : 【站号节点】标识符 `ST` + 内部空格 + 数据 `0012341234` + 尾部空格 。
        
    - `H` : 【分类码节点】无标识符 + 数据 `H` + 尾部空格 。
        
    - `TT 1707181112` : 【观测时间节点】标识符 `TT` + 内部空格 + 数据 `1707181112` + 尾部空格 。
        
    - `PJ 00005` : 【降水节点】标识符 `PJ` + 内部空格 + 格式化数据 `00005` + 尾部空格 。
        
    - `Z 0125000` : 【水位节点】标识符 `Z` + 内部空格 + 格式化数据 `0125000` + 尾部空格 。
        
    - `VT 1091` : 【电压节点】标识符 `VT` + 内部空格 + 格式化数据 `1091` + 尾部空格 。_(规约要求最后一项末尾保留空格)_
        
3. **结尾段 (Tail)**:
    
    - `[0x03]` : 报文结束符 (JSON 中 `format: "HEX_CTRL"`)
        
    - `ABCD` : **动态校验码** (`sys_calc_crc` 触发，单片机对全包数据进行 CRC-16 计算后转为 ASCII 填入)

## 7. 配置约束与业务逻辑映射
### 7.1 报文类型与链路模式映射表

为保证网关通讯行为符合国标，配置软件在生成 `meta_config` 的 JSON 时，必须严格遵循《SL651-2014》 6.3.1.2 节对链路模式的应用规定。下表为配置软件 UI 交互时的合法模式约束逻辑：

| **报文类型 (message_type)**   | **功能码 (function_code)**   | **允许的链路模式 (protocol_mode)** | **规约依据说明**                                                                    |
| ------------------------- | ------------------------- | --------------------------- | ----------------------------------------------------------------------------- |
| **测试报 / 定时报 / 加报报 / 小时报** | `30` / `32` / `33` / `34` | **M1, M2**                  | 规约明确指出，M1 和 M2 均可用于发送自报报文（包含上述四种报文）。区别在于：配置为 M1 时单向发送不等待响应，配置为 M2 时必须等待中心站确认。 |
| **均匀时段水文信息报 / 人工置数**      | `31` / `35`               | **M1, M2, M3**              | 这两类数据既可以作为单帧发送（适用 M1/M2），也因为数据量可能较大而作为多帧发送，此时适用 M3（多包发送/确认）模式。                |
| **中心站查询响应 / 参数配置响应**      | `37`~`3A`, `41`, `43`     | **M4**                      | 凡是由中心站发起查询或设置请求，遥测站被动响应的业务，必须且只能使用 M4（查询/响应）模式。                               |
| **链路维持报**                 | `2F`                      | M1                          | 遥测站主动发出的心跳包，仅用于向中心站报告设备在线状态，单向发送即可，无需中心站确认响应，适用 M1 模式。                        |

_(注：配置软件开发者需将此表固化为 `ui_rules.json` 逻辑模板，用户在界面选择报文类型时，单选框应自动禁用不合法的 M1~M4 选项。)_

#### 7.2 正文要素生成规则与时序约束 (针对 Payload)

上位机软件在生成 `payload.fields` 数组时，不能让用户随意乱排顺序，必须在软件底层强制执行以下国标规约逻辑：

- **时序与动态节点插入约束**：为落实本规范 **[第 4.4 节]** 所述的异构时间组包机制，上位机必须对比各要素绑定的数据源。若时间源发生变更，上位机必须自动生成对应的 `TT` 标识符节点，且 **`TT` 节点必须严格排列在其关联的数据要素之前**。
    
- **必填项前置**：上位机软件在编译 JSON 时，必须自动在 `payload` 的最前端生成“流水号”和“发报时间”，这两个字段对用户不可见、不可删减。
    
- **分隔符补全**：除了流水号和发报时间，上位机在生成其他 SL651 要素节点时，必须自动在 JSON 的 `separator` 字段填入 `" "`（空格符），以保证 ASCII 模式下的合法性。
    

#### 7.3 系统保留字段防篡改约束 (针对 Header 和 Tail)

上位机配置界面必须对部分核心字段进行“只读”或“底层接管”保护：

- **动态长度与校验**：报头中的 `message_flag_and_length` 和报尾中的 `checksum`，在生成 JSON 时，其 `source` 必须强制绑定为 `sys_calc_length` 和 `sys_calc_crc`。**绝对禁止**开放输入框让用户手工填写这两个字段的 Value。
    
- **控制字符保护**：诸如 SOH (`01`), STX (`02`), ETX (`03`) 等帧控制符，其 `format` 必须强制锁定为 `"HEX_CTRL"`，防止被意外篡改为普通字符串。
