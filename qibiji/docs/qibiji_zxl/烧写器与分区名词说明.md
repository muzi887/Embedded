# 烧写器与分区名词说明（ST-Link / J-Link / SWD / JTAG / B / A1 / A2）

> **文档定位**：本工程（STM32F103VET6）烧写与分区相关的基础名词速查。数值均为本工作区当前配置实测值，理论背景不展开。

---

## 一、烧写器与调试接口

### 1. ST-Link

ST 官方调试/烧写器，**只支持 ST（STM32）芯片**。本工程用的是 **ST-LINK/V2**，Keil 配置三处（已实测可用，详见《OTA重构操作建议.md》阶段一）：

1. Options → Debug：Use = `ST-LINK Debugger`，Port = **SW**（读到 IDCODE `0x1BA01477` 即连接正常）；
2. Flash Download：Download Function = **Erase Sectors**（绝不能 Erase Full Chip，否则把 boot 和 app 一起擦掉）；
3. Programming Algorithm = `STM32F10x High-density Flash`（512K，匹配 VET6）；**RAM for Algorithm = Start `0x20000000` / Size `0x5000`**——这个算法要 20KB 运行内存，给小了报 `Flash Download failed - Cortex-M3`。

### 2. J-Link

SEGGER 的第三方调试器，支持几乎所有厂商的芯片，商用需授权。本工程**没有使用**。同类的 ULINK2 是 Keil 自家产品——如果 Keil 里选了 ULINK2 而手头插的是 ST-Link，会直接找不到目标，选回 ST-LINK Debugger 即可。

### 3. SWD

Serial Wire Debug，ARM 标准的两线调试接口，JTAG 的精简替代，本工程实际使用：

| SWD | 本工程引脚 | 作用 |
|---|---|---|
| SWDIO | PA13 | 数据 |
| SWCLK | PA14 | 时钟 |
| GND / 3V3 | — | 供电与地 |

本工程 boot 和 app **都用 SW 四线烧写**。SWD 同时可以烧 boot（0x08000000）和 app（0x0800E000）——两个工程 IROM1 起始不同，各点一次 Download，互不覆盖对方分区。

### 4. JTAG

Joint Test Action Group，IEEE 1149.1 边界扫描标准，最早的 ARM 调试/烧写接口，20 针排针（核心信号 4+1 线：TCK / TMS / TDI / TDO / nTRST，余下为 GND 与供电）。本工程**没有使用**，Keil 的 Port 保持 SW。

与 SWD 的关系（VET6 同一组引脚复用，二者只能选其一）：

| JTAG 信号 | VET6 引脚 | 备注 |
|---|---|---|
| JTMS | PA13 | 与 SWDIO 复用 |
| JTCK | PA14 | 与 SWCLK 复用 |
| JTDI | PA15 | 仅 JTAG 使用 |
| JTDO | PB3 | 仅 JTAG 使用 |
| NJTRST | PB4 | 仅 JTAG 使用 |

选 SW 后 PA15 / PB3 / PB4 从 JTAG 中释放，可腾作 GPIO；选 JTAG 则多占三根引脚、换来的只是 TDI/TDO 双向扫描等边界扫描能力，烧写调试功能上 SWD 已够用——这就是本工程选 SW 的原因。

## 二、Flash 分区

### 1. B 区 / bootloader

`qibiji_boot` 工程，常驻 **0x08000000，56KB**，**只能用 SWD 烧写**（它自己不会联网下载自己）。每次上电最先运行，职责只有三件：

1. **看 OTA_flag**（EEPROM）：A2 区有新固件（标志 ≠ `a1a1a1a1`）→ 把 A2 搬运到 A1，搬运成功后自动把 UPDATE_flag 置 0；
2. **看 UPDATE_flag**（EEPROM 240）= 1 → 走联网升级：LCD 显示"在线升级/连接成功/申请最新固件"，`putVersion` 上报 EEPROM 里的版本号给服务器比对，需要升级就分包下载到 A2，复位后由第 1 步生效；
3. **跳转 A1**：串口打印 `jump to a1!` 后把 CPU 交给应用。跳转只做"设栈顶 + 跳复位向量"，向量表重定位、喂看门狗是 A1 应用自己的责任。

跳转失败（A1 空片）时会落到 OTA 状态机，这是空片设备的恢复入口。

### 2. A1 区

**运行区**，**0x0800E000 起，200KB**。qibiji_zxl 的 IROM1 起始必须是 `0x0800E000`（Size `0x32000` = 200KB），`VECT_TAB_OFFSET` 必须是 `0x0E000`，否则跳过去后向量表、常量全错位。EEPROM 里 OTA_flag = `a1a1a1a1` 就表示"当前有效固件在 A1"——boot 启动打印 `OTA_ver = V1.0.0,a1a1a1a1,255` 中的第二段就是它。

### 3. A2 区

**备份区**，**0x08040000 起，200KB**，OTA 升级的下载目标。新固件先落到这里，**不直接运行**；复位后由 bootloader 搬运到 A1 才生效。注意 A1 写满会覆盖 A2（boot 侧已有护栏拦截）。

（0x08072000 起还有 56KB 未分配。）

## 三、一张图串起来

```
上电 → B 区 bootloader
         │
         ├─ OTA_flag≠a1a1a1a1？ → A2 搬运到 A1，UPDATE_flag 置 0
         │
         ├─ UPDATE_flag=1？ → 联网 OTA：报版本 → 下载到 A2 → 复位重来
         │
         └─ 否 → jump to a1! → A1 应用（qibiji_zxl）
```

- **SWD 烧写**：开发期把 boot 和 app 分别烧进 B 区 / A1 区；
- **OTA 升级**：运行期新固件经 A2 中转到 A1，SWD 不再参与；
- **UPDATE_flag 开闸**：平台 config 通道 `OTAEnableFlagConfig` → A1 应用写 EEPROM 240（已实测通过）；关闸 = 下发 `false` 或一次升级成功后 boot 自动置 0。
