## 一、CSQ 判定缺陷

### 现象

串口持续输出 `+CSQ: 99,99`（模块未注册网络、无信号），但状态机把它当成"CSQ 查询成功"，`g_at_flag_csq` 被置 1。

### 根因

原回调只做子串匹配，不解析数值：

```c
static void s_on_csq(char *data, uint16_t len)
{
    if (strstr(data, "+CSQ") != NULL)
        g_at_flag_csq = 1u;      /* 99,99 也算成功 */
    ...
}
```

`+CSQ` 的 rssi 字段语义（3GPP TS 27.007）：`0` = ≤-113dBm（基本无服务）、`1~31` 有效（`dBm = -113 + 2×rssi`）、`99` = 未知/不可测。把 `99` 判为成功会掩盖真实的无信号状态。

### 修复

在 [gprs_at.c](../../../qibiji_zxl/HARDWARE/GPRS/gprs_at.c) 中新增解析函数，只在真出现 `+CSQ:` 子串时按数值判定：

```c
static uint8_t s_csq_signal_ok(const char *data)
{
    const char *p = strstr(data, "+CSQ:");
    uint16_t v = 0u;
    uint8_t  digits = 0u;

    if (p == NULL)
        return 0u;
    p += 5;
    while (*p == ' ')
        p++;
    while (*p >= '0' && *p <= '9')
    {
        v = (uint16_t)(v * 10u + (uint16_t)(*p - '0'));
        p++;
        digits++;
        if (digits > 3u)
            return 0u;
    }
    if (digits == 0u)
        return 0u;
    return (v >= 1u && v <= 31u) ? 1u : 0u;
}

static void s_on_csq(char *data, uint16_t len)
{
    if (strstr(data, "+CSQ:") != NULL)
        g_at_flag_csq = s_csq_signal_ok(data) ? 1u : 0u;
    GPRS_Printf("[GPRS] CSQ: %.*s\r\n", (int)len, data);
}
```

### 要点

- 条件必须是 `strstr(data, "+CSQ:")`，不能只判 `"+CSQ"`，否则应答帧错位时（见第二节）会误判；
- 不使用 `atoi()`，避免额外引入 `<stdlib.h>` 和异常输入风险；
- 行为变化：无信号时不再进 `ST_AT_WAIT` 的"初始化完成"，3 次重试后进入 30 分钟退避，不再空转发业务包。

### 验证

| 场景 | 期望 | 实测 |
|---|---|---|
| 有信号 | `+CSQ: 20~23,99`，标志置 1 | 通过（实测 20/21/22/23） |
| 无信号 | `+CSQ: 99,99`，标志保持 0 | 通过 |

## 二、AT 应答帧与回调错位

### 现象

日志出现"回调收到的内容不属于该命令"：

```
[GPRS] RX[44] usr.cn# +ICCID:89861124204085195798 OK
[GPRS] RX[28] usr.cn# +CSQ: 99,99 OK
[GPRS] CSQ: usr.cn# +ICCID:89861124204085195798   ← CSQ 回调收到 ICCID 内容
```

### 根因

AT 应答是**按先进先出顺序**匹配回调的。当某条命令超时未收到回包（模块正重启、无信号等），队列里留下"空槽"，后续每收到一帧就整体错位一格，于是 ICCID 的回包被喂给了 `s_on_csq`，`s_on_csq` 的回包喂给下一个回调。

诱因是丢回包：日志中模块自重启前后，成片的 `send at-->` 无任何 `RX`。

### 影响

- 错误触发状态转换（例如误以为某命令成功）；
- 若回调里做"置 0"动作（如 CSQ 修复的第一版），错位帧会误清正确标志。

### 处理

1. 回调内部只处理"确实属于自己"的帧（校验前缀，如 `+CSQ:`），不匹配时不动状态；
2. 可选项：在 `GPRS_AT_OnBanner()` 里调用 `UartTx_Queue_Init()`，模块重启即丢弃在途项，缩短错位窗口（注意会丢包）；
3. 若后续要彻底解决，需在 AT 框架层为每条命令建立"应答特征指纹"，而非纯 FIFO 匹配。

## 三、4G 模块周期性自重启

### 现象

- `WH-LTE-7S1` banner 反复出现，间隔 10~77 秒不等；
- `pc4=0 pc5=0`（LINKA 始终为低），MQTT 会话从未建立；
- `+CSQ` 绝大多数为 `99,99`，偶发 `20~23`；
- 两次 60s 离线硬复位 4G，均未恢复。

### 排查过程

| 假设 | 证据 | 结论 |
|---|---|---|
| ① 供电不足（4G 发射峰值 2A 导致 VBAT 跌落） | 链路恢复后 MQTT 持续发射，模块 3 分钟无重启；发射电流最大的时刻反而最稳定 | **排除** |
| ② 离线探询（每 5s 灌 7+3 条 AT）打断模块启动 | 恢复时仍跑旧固件（无静默窗口），照常注册成功 | **排除** |
| ③ 弱覆盖 + 模块自身重注册策略 | 34 次 CSQ 仅 3 次有效；重启间隔不规律（符合"每次注册尝试耗时不同"）；无外部干预下自助注册成功 | **成立** |

### 结论

模块在正常重试，只是信号差到需要尝试二十余次。代码侧无需修改；两次硬复位都没救活、最后自己好了，说明该问题不在固件处理逻辑内。

### 后续建议

- 优先确认现场信号（挪位置/换天线）；
- 若长期弱覆盖，可考虑加外置天线或提高重试退避上限，但不要用"缩短硬复位间隔"来应对——已验证无效。

## 四、离线探询静默窗口

### 目的

模块刚重启时需要 8~10 秒完成射频初始化与网络注册，此期间的 AT 灌包虽未证实有害，但属于无意义干扰，且会造成应答错位（见第二节）。

### 实现

**注意**：静默窗口只能在"收到 banner"这个边沿事件里设置一次，不能写在探询函数里——`g_atflag_online` 在离线期间一直为 1，写在探询函数里会每轮延长窗口，导致探询被永久禁用。

```c
/* 状态变量区 */
#define PROBE_QUIET_AFTER_BANNER_MS   10000u
static uint32_t s_probe_quiet_until = 0u;

void GPRS_AT_OnBanner(void)
{
    g_atflag_online = 1u;
    s_probe_quiet_until = g_sys_ms + PROBE_QUIET_AFTER_BANNER_MS;
    GPRS_Printf("[GPRS] module banner seen -> atflag_online=1, probe quiet\r\n");
}

static void s_offline_probe(void)
{
    ...
    /* 模块刚重启：等它完成射频初始化/网络注册，期间不发任何 AT */
    if ((int32_t)(g_sys_ms - s_probe_quiet_until) < 0)
        return;
    ...
}
```

### 参数取舍

| 取值 | 效果 |
|---|---|
| 10000ms（推荐） | 覆盖典型启动时间，重启周期 10~16s 时每轮仍留有观察窗口 |
| 30000ms | 若模块 10~20s 就重启一次，探询会被**永久压制**，日志中只剩 banner，失去诊断数据 |

有符号比较 `(int32_t)(g_sys_ms - s_probe_quiet_until) < 0` 可正确处理 `g_sys_ms` 回绕（约 49 天）。

## 五、未供电 ST-Link 造成的分压与背光异常

### 现象

只拔掉 ST-Link 与电脑相连的 USB、保留与主板相连的引脚时，按按键 LCD 背光不亮；把主板侧接线也拔掉后正常。

### 代码侧的背光原理

背光只有一条通路：**MCU 的 PA0 → 屏上背光驱动 → LED**。

```c
#define LCD_BL      PAout(0)   /* PA0，推挽输出 50MHz */
#define LCD_BL_ON   1u         /* 高电平点亮 */
#define LCD_BL_OFF  0u
```

三个函数构成状态机：

| 函数 | 调用点 | 作用 |
|---|---|---|
| `LCD_BACKLIGHT_Init()` | main.c:82 | 计数清零、PA0 置高 → 上电默认亮 |
| `LCD_BACKLIGHT_Kick()` | main.c:52（每次按键） | 计数清零；仅在灭状态才写 PA0 → 任意键点亮 |
| `LCD_BACKLIGHT_Tick()` | main.c:112（10ms 节拍） | 每 10ms 累加，满 3000 次（30s）关背光 |

`LCD12864_Init()` 内部先关背光（等 ST7920 上电稳定 1.5s），初始化完成后再置高；随后 `LCD_BACKLIGHT_Init()` 再置高并清零计时，因此**上电默认亮 30 秒，之后任意按键重新点亮 30 秒**。

`s_idle_ticks` 用 uint16 并做饱和处理（`if (s_idle_ticks < BL_TICKS) s_idle_ticks++`），不会回绕。

### 原因

**拔 USB 只切断了 ST-Link 自己的电源，它的引脚还插在板子上，成了主板的额外负载。**

ST-Link 每个引脚内部都有一对 ESD 保护二极管（引脚→自身 3.3V 轨、GND→引脚）。ST-Link 自身 3.3V 为 0V 时，主板信号会经"引脚 → ESD 二极管 → ST-Link 内部电路 → GND"漏入 ST-Link，与主板内的上拉/驱动形成**分压**，把节点电平拉到中间值甚至接近 0V，背光使能因此失效。

### 分压的含义

两个电阻串联、从中间取电压：

```
        Vin (3.3V)
          │
        [R1]        ← 上分压：主板内阻/线阻/二极管等效电阻
          │
          ├────► Vout
          │
        [R2]        ← 下分压：未供电 ST-Link 那一路到地的等效电阻
          │
         GND

Vout = Vin × R2 / (R1 + R2)
```

| R1 | R2 | Vout |
|---|---|---|
| 1kΩ | 1kΩ | 1.65V（腰斩） |
| 1kΩ | 100Ω | 0.30V（几乎拉平） |
| 1kΩ | 断开 | 3.3V（无负载，正常） |

数字电路判高电平通常要求 >0.7×VDD（约 2.3V），被分压到中间值后既非高也非低，行为不可预测。

### ESD 保护二极管为什么在断电时仍然导通

ESD = ElectroStatic Discharge（静电放电），几千伏的瞬间电压足以击穿 MOS 栅极氧化层，所以每颗芯片的每个 I/O 都有出厂内置的保护二极管：

```
              VDD（芯片自己的电源）
                │
                ├──►|──┐      D1：引脚电压 > VDD 时导通，向上泄放
                │      │
   外部信号 ────┴──────┼────► 内部电路
                       │
                ┌──────┴──◄──┐  D2：引脚电压 < GND 时导通
                │            │
               GND
```

正常 0~3.3V 时两个二极管都不导通，不影响功能；异常电压时导通泄放。**它们在芯片断电时依然存在**，所以未供电设备的引脚一旦挂上带电信号，就会经 D1 向它自己的（0V）电源轨漏电。

### 背光不亮的三种可能及判读

| 可能 | 代码侧表现 | 是否符合本现象 |
|---|---|---|
| A. CPU 卡死在 `while(1)` | `LCD_BACKLIGHT_Tick()` 跑不到，**背光保持常亮**，不会熄灭 | **不吻合**——卡死只会让背光一直亮 |
| B. MCU 被按在复位状态（NRST 被拉低） | 程序未启动，PA0 保持低电平，背光灭、按键无响应 | **吻合** |
| C. PA0 或背光供电被外部拉低 | 电平被分压，LED 电流不足 | 吻合，但 PA0 不在 SWD 线上，需硬件确认 |

对照 A 与 B 是关键：**若只是程序卡死，背光会常亮而不是不亮**。因此本次现象更接近 B——未供电 ST-Link 把 SWD/NRST 拉低，MCU 停在复位状态，`LCD_BACKLIGHT_Init()` 根本没执行。这也解释了拔掉 USB 期间串口长时间无输出。

### 测量确认方法

背光不亮时用万用表测三个点：

| 测点 | 判断 |
|---|---|
| NRST 对地电压 ≈ 0V | MCU 被按在复位（原因 B） |
| PA0 对地电压在 1~2V 之间 | 电平被分压（原因 C） |
| 背光 LED 正极对地电压为 0V | 背光供电缺失 |

### 操作规则

1. 未供电时 **整根拔掉 ST-Link**，不要只拔电脑端 USB；
2. 或至少断开 SWDIO / SWCLK / GND 这几根；
3. 若需保留接线，就让 ST-Link 保持供电并退出调试会话（此时引脚在正常驱动，不是负载）；
4. 避免长期"半连接"——主板信号经 ESD 二极管持续灌入未上电的 ST-Link 属于电流倒灌，可能损伤 IO。

### 判断 ST-Link 是否在给板子供电

看复位标志可以区分"是否断电"，但**不能**区分"板子在运行"还是"被按在复位"：

| 重插后首次启动读到 | 含义 |
|---|---|
| `[WDG] no IWDG reset` | 期间发生过上电复位（POR），板子当时确实断电 → ST-Link 参与供电 |
| `[WDG] reset by IWDG` | 期间未断电：板子可能在继续运行，也可能被拉低 NRST 停在复位（保持复位不会清除 CSR 标志） |

要区分后两种情况，需另测 NRST 电平或观察 LCD/按键是否响应。

## 六、EEPROM 清空后的自愈流程

清空（全片 `0xFF`）后无需手工重写，上电自动播种：

```
AT24CXX_Check()
  → 读标记字节 ≠ 0x55 → 写入 0x55（1 字节）
  → 检测数据区仍为空白 → paraToEeprom() 播种默认值（7 字节）
dcmotor_param_load()
  → 版本号不符 → 再次播种（幂等）
gprs_config_load()
  → 凭据槽空白 → 回退到编译期宏（pk001 / dev001 / 服务器地址）
```

串口可见：

```
24C02 blank: seed defaults via paraToEeprom
gate param load: maxheight=1000 maxturns=80 warn_curr=3500
```

注意：**EEPROM 清空不影响 4G 模块的联网配置**。MQTTSVR、MQTTMOD、订阅/发布主题都保存在模块内部，与 MCU 的 24C02 无关。

## 七、其他发现

### 1. 远程配置保存函数无调用者

以下函数只有定义、全工程无调用：

- `dcmotor_param_save_warn_curr()` / `save_maxheight()` / `save_maxturns()`（dcmotor_param.c:82/88/94）
- `gprs_store_write_str()`（gprs_config_store.c:67）

影响：远程下发"修改堵转阈值/最大高度/圈数"目前**不会真正写入 EEPROM**，平台改参数掉电即丢失。接入配置下发时需补上调用。

### 2. 串口日志通道

日志经 ST-Link 的虚拟串口（VCP）输出，拔掉 USB 后日志必然中断，出现空档。空档期间板子**可能仍在运行**，也可能因未供电 ST-Link 拉低 NRST 而停摆（见第五节），两者需靠 `RCC_CSR` 复位标志区分。若需脱机观察日志，应使用独立 USB-TTL 模块接 PA9/GND。

### 3. `g_sys_ms` 读数的量化特性

`g_sys_ms` 每 10ms 加 1，读数是"期间跨过几个 10ms 节拍边界"，不是精确耗时：

- 真实耗时 10.05ms 可能读到 10ms 或 20ms（取决于起点相位）；
- 判断"是否超过阈值"时应留出至少一个节拍的余量；
- 对照毫秒级精度时，用串口时间戳比用 `g_sys_ms` 更可靠。
