# 按键检测方式：定时轮询与按键中断

> 这份文件说明两件事：**目标版采用哪一种按键检测方式**，以及**另一种方式在本工程的硬件上为什么做不到**。
> 全文按「是什么、怎么跑、为什么这样选、另一种会怎样」的顺序写，代码位置与硬件依据统一放在第 10 节。
>
> **版本界定（重要）**：`qibiji_zxl/` 里的代码已经撤回到重构前的骨架状态（`git` 提交 `29dab9f empty_qibiji_zxl`），`main.c` 是空 `while(1)`，`HARDWARE/TIMER/` 不存在。本文件所说的「目标版」是指重构完成后的代码，其完整内容在 `docs/qibiji_zxl/KEY重构操作建议.md` 第 2~7 节，另有一份物理备份在临时目录。本文件描述的是目标设计，不是当前磁盘上正在编译的代码。

---

## 1. 结论

**目标版的按键检测采用定时轮询（扫描），不采用按键外部中断（EXTI）。**

整个系统只有一个中断：`TIM3` 的 10ms 定时器中断。它不检测按键、不读引脚，只把一个标志位置 1。真正读引脚、消抖、生成事件、取事件、分发，全部在主循环里完成。

准确归类是：**定时器中断提供固定时基 + 主循环扫描检测按键**。

| 中断类型 | 目标版是否存在 | 职责 |
|---|---|---|
| 定时器中断 `TIM3_IRQHandler` | 有，且唯一 | 每 10ms 置 `s_tick_10ms = 1`，不读引脚 |
| 按键外部中断 `EXTIx_IRQHandler` | 无 | — |

容易混淆的是「中断」这个词在本工程里有两层含义：说「目标版有中断」指的是 TIM3；说「按键不是中断检测」指的是没有 EXTI。两者不矛盾。按键部分不需要编写任何中断服务程序。

## 2. 两种方式的界定

### 2.1 定时轮询（扫描）

由定时器给出固定时间间隔，程序在每个时间点主动读取一次所有按键引脚的电平，用连续多次采样一致来判定一次有效按下。检测动作发生在主循环，触发条件是「时间到了」，与按键是否按下无关。

### 2.2 按键中断（EXTI）

把按键引脚配置成外部中断线，引脚电平发生指定边沿（本工程按键为低电平有效，对应下降沿）时由硬件向 NVIC 发出请求，CPU 暂停当前流程进入中断服务程序。检测动作的起点是「电平跳变」，与定时器无关。

### 2.3 两者的结构差异

| 项目 | 定时轮询 | 按键中断 |
|---|---|---|
| 触发源 | 定时器溢出，周期性发生 | GPIO 边沿，按键动作时才发生 |
| 读引脚的位置 | 主循环 `KEY_Tick()` | 中断服务程序，或由中断置标志后回到主循环 |
| 消抖的位置 | 状态机在连续采样中完成 | 无法直接在 ISR 内完成，需要额外的定时回读 |
| 不按键时的开销 | 每 10ms 读一次 5 路引脚 | 零 |
| 与本工程的关系 | 目标版采用 | 未采用 |

## 3. 目标版的定时轮询怎么跑

按执行顺序分四段，代码均取自目标版。

### 3.1 中断侧：只置标志

`HARDWARE/TIMER/timer.c`

```c
static volatile uint8_t s_tick_10ms;

void TIM3_IRQHandler(void)
{
    if (TIM_GetITStatus(TIM3, TIM_IT_Update) != RESET)
    {
        TIM_ClearITPendingBit(TIM3, TIM_IT_Update);
        s_tick_10ms = 1;   /* 中断里只置标志，业务一律留给主循环 */
    }
}
```

这个中断里没有 `KEY_ReadPins()`、没有状态机、没有队列操作、没有串口发送。它的全部作用是提供一个与按键无关的、不随主循环负载变化的时间基准。

时基参数（`TIM3_10ms_Init()`）：`SYSCLK = 72MHz`，`TIM_Prescaler = 7199`，`TIM_Period = 99`，即 `72MHz / 7200 = 10kHz`，计 100 个脉冲 = 10ms。

### 3.2 主循环侧：取到节拍才采样

`USER/main.c`

```c
while (1)
{
    /* 1) 固定节拍：每 10ms 采样一次，去抖时间与主循环速度无关 */
    if (Tick_10ms_Take())
        KEY_Tick();

    /* 2) 取走一个事件，取走即清；没有事件就什么都不做 */
    key = KEY_Pop();
    if (key != KEY_NONE)
        App_DispatchKey(key);

    /* 3) 后续模块的 _Process() 依次加在这里 */
}
```

`Tick_10ms_Take()` 读到标志后把标志清 0 并返回 1。两个动作的节奏不同：**采样是每 10ms 一次，取事件是主循环每圈一次**。事件可以在两次采样之间的任意一圈被取走并分发。

### 3.3 采样侧：位图 → 状态机 → 队列

`HARDWARE/KEY/key.c`

```c
static uint8_t KEY_ReadPins(void)
{
    uint8_t bits = 0;

    if (KEY_PIN_UP     == 0) bits |= (uint8_t)(1u << KEY_IDX_UP);
    if (KEY_PIN_DOWN   == 0) bits |= (uint8_t)(1u << KEY_IDX_DOWN);
    if (KEY_PIN_STOP   == 0) bits |= (uint8_t)(1u << KEY_IDX_STOP);
    if (KEY_PIN_SET    == 0) bits |= (uint8_t)(1u << KEY_IDX_SET);
    if (KEY_PIN_CANCEL == 0) bits |= (uint8_t)(1u << KEY_IDX_CANCEL);

    return bits;
}
```

一次读齐 5 路电平，拼成 5 位位图（bit = 1 表示该键此刻按下，引脚低电平有效）。`KEY_Tick()` 用 `for (i = 0..4)` 对每颗键跑一个独立状态机：

```
松开 IDLE --连续 3 拍按下--> 报一次事件 + 锁住 PRESSED --松开--> IDLE
                └─ 消抖期间任一拍松开，立即退回 IDLE 重新计数
```

`KEY_DEBOUNCE_TICKS = 3`，配合 10ms 节拍就是 30ms 消抖。计数用饱和写法（`if (f->cnt < KEY_DEBOUNCE_TICKS) f->cnt++`），进入 `KEY_ST_PRESSED` 后不再产生事件，所以长按不连发；必须完全松开才能触发下一次。确认按下时调用 `KEY_QueuePush(s_key_code[i])` 把键码写入模块私有的环形队列，主循环用 `KEY_Pop()` 取出。

### 3.4 一次按下的时序

| 时刻 | TIM3 中断 | 主循环动作 | STOP 键状态机 |
|---|---|---|---|
| t = 0ms | 置标志 | `KEY_Tick()` 采样，STOP 按下 | `IDLE → DEBOUNCE`，`cnt = 1` |
| t = 10ms | 置标志 | `KEY_Tick()` 采样，仍按下 | `DEBOUNCE`，`cnt = 2` |
| t = 20ms | 置标志 | `KEY_Tick()` 采样，仍按下 | `DEBOUNCE`，`cnt = 3` |
| t = 30ms | 置标志 | `KEY_Tick()` 采样，仍按下 | `cnt` 已达 3 → `PRESSED`，`KEY_QueuePush(KEY_STOP)` |
| 同一圈稍后 | — | `KEY_Pop()` 返回 `KEY_STOP` → `App_DispatchKey()` 打印 `KEY: STOP` | 队列减一 |
| t = 40ms ~ 6s | 每 10ms 一次 | 持续采样，无新事件 | 保持 `PRESSED`，计数饱和 |
| 松开后的第一拍 | 置标志 | 采样到松开 | `PRESSED → IDLE`，`cnt = 0`，可再次触发 |

这个时序成立的前提只有一个：采样间隔固定。若改成主循环每圈采样，「数 3 次」的时间会随显示、通讯、EEPROM 等模块的负载变化，30ms 消抖不再成立，行为不可复现。这也是目标版必须引入 TIM3 的原因。

## 4. 如果改成按键中断，代码会是什么样

以下只用于说明另一种方式的结构，**不是目标版代码，不要写进工程**。以 STOP 键（PA11，低电平有效 → 下降沿触发）为例，一个 EXTI 方案至少包含四步配置和一个中断服务程序：

```c
/* 1) 打开 AFIO 时钟，把 EXTI11 接到 PA11 */
RCC_APB2PeriphClockCmd(RCC_APB2Periph_AFIO, ENABLE);
GPIO_EXTILineConfig(GPIO_PortSourceGPIOA, GPIO_PinSource11);

/* 2) 配置 EXTI11 为下降沿中断 */
EXTI_InitTypeDef exti;
exti.EXTI_Line    = EXTI_Line11;
exti.EXTI_Mode    = EXTI_Mode_Interrupt;
exti.EXTI_Trigger = EXTI_Trigger_Falling;   /* 按下时引脚由高变低 */
exti.EXTI_LineCmd = ENABLE;
EXTI_Init(&exti);

/* 3) 使能 NVIC 通道：PA11 落在 EXTI15_10_IRQn */
NVIC_InitTypeDef nvic;
nvic.NVIC_IRQChannel = EXTI15_10_IRQn;
/* ...优先级、Cmd = ENABLE... */
NVIC_Init(&nvic);

/* 4) 中断服务程序 */
void EXTI15_10_IRQHandler(void)
{
    if (EXTI_GetITStatus(EXTI_Line11) != RESET)
    {
        EXTI_ClearITPendingBit(EXTI_Line11);
        /* 这里只能置标志或记录时间；30ms 消抖不能在 ISR 内完成 */
    }
}
```

上面用到的符号（`GPIO_EXTILineConfig`、`GPIO_PinSource11`、`EXTI_Trigger_Falling`、`EXTI_Line11`、`EXTI15_10_IRQn`）在 `qibiji_zxl/STM32F10x_FWLib/` 中都存在，配置本身可行。问题不在语法，而在本工程的硬件分配和消抖需求，见第 5 节。

注意第 4 步：即使采用 EXTI，中断里也无法完成 30ms 消抖。ISR 内不能阻塞等待，机械抖动又会在边沿上产生多次跳变。可行做法仍是「中断里置标志，另外用定时器每 10ms 回读引脚确认」——**绕一圈还是需要定时扫描**。

## 5. 本工程的 5 个引脚，EXTI 方案为什么不成立

### 5.1 引脚到 EXTI 线的映射

`qibiji_zxl/HARDWARE/KEY/key.c` 目标版的引脚分配：

| 丝印 | 键码 | 引脚 | 对应 EXTI 线 | 对应中断向量 |
|---|---|---|---|---|
| K1 UP | `KEY_UP` | PD15 | EXTI15 | `EXTI15_10_IRQHandler` |
| K2 DOWN | `KEY_DOWN` | PA15 | EXTI15 | `EXTI15_10_IRQHandler` |
| K5 STOP | `KEY_STOP` | PA11 | EXTI11 | `EXTI15_10_IRQHandler` |
| K4 SET | `KEY_SET` | PA12 | EXTI12 | `EXTI15_10_IRQHandler` |
| K3 CAN | `KEY_CANCEL` | PC9 | EXTI9 | `EXTI9_5_IRQHandler` |

5 颗键只占 4 条 EXTI 线（9 / 11 / 12 / 15）和 2 个中断向量（`EXTI9_5_IRQn = 23`、`EXTI15_10_IRQn = 40`）。

### 5.2 硬件冲突：PA15 与 PD15 抢同一条线

STM32F103 的 EXTI 线按**引脚号**分配，不按端口。每条线由 AFIO 的 `EXTICR` 寄存器里一个 4 位字段选择端口来源，一个字段只能填一个值。以 EXTI15 为例：

```
AFIO_EXTICR4_EXTI15       0xF000   /* 字段位置 */
AFIO_EXTICR4_EXTI15_PA    0x0000   /* 选 PA15 */
AFIO_EXTICR4_EXTI15_PD    0x3000   /* 选 PD15 */
```

`EXTI15` 只能选 PA15 **或** PD15，不能同时。也就是说 K1 UP（PD15）和 K2 DOWN（PA15）不可能各自拥有独立的外部中断。结果只能是：其中一颗用 EXTI，另一颗仍然靠读 IDR 电平判断——**等于回到了扫描**，而且两套机制并存。

这条约束是芯片硬件决定，改代码绕不过去；除非改 PCB 把其中一个键换到别的引脚号。

### 5.3 中断向量共享，ISR 内仍要逐个判别

`EXTI15_10_IRQHandler` 服务 EXTI10~15 共 6 条线。本工程的 PA11、PA12、PA15（以及若选 PD15 时的第 15 号线）全部落在这一个 ISR 里。进入中断后必须逐条 `EXTI_GetITStatus()` 才能知道是哪颗键，再回读 IDR 区分第 15 号线上的两个端口。中断「直接知道按下的是谁」这个优势，在这套引脚分配上不存在。

### 5.4 机械抖动与消抖的位置矛盾

按键是机械触点，按下和松开瞬间会在几毫秒内产生多次电平跳变。若配置成下降沿触发，一次按下可能触发多次中断。要滤掉这些跳变，必须做 30ms 连续确认，而：

- ISR 内不能调用 `delay_ms()` 或任何阻塞等待；
- 若改成「中断里记录时间戳，主循环延时后再读引脚」，仍然需要一个时间基准；
- 若改成「中断里临时关闭该 EXTI 线，定时器到点再打开」，同样需要定时器，且增加了开关中断线的状态管理。

结论：EXTI 方案在本工程里**无法独立完成按键识别**，最终还是要配一个定时器并定期读引脚，即「扫描 + 额外的中断配置」。

### 5.5 PA15 的调试接口复用

PA15 复位后默认复用为 JTAG 的 JTDI。目标版沿用原工程接法，只读 IDR 电平，不禁用 JTAG。若要让 PA15 参与 EXTI，还需先做 `GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE)` 并改用 SWD 调试，属于额外的硬件/调试配置变更。

### 5.6 共享数据的并发问题

目标版的 `s_fsm[5]`、`s_queue[4]`、`s_q_head/tail/count` 都是模块私有的普通 `static` 变量，Push 与 Pop 都在主循环同一上下文执行，因此不需要加锁。`KEY重构操作建议.md` 第 9 节第 2 条明确规定：`KEY_Tick()` 与 `KEY_Pop()` 必须在主循环同一上下文调用，**不要在中断里调 `KEY_Pop()`**。

若改成 EXTI，中断侧要写状态或队列，主循环侧要读队列，这些变量就得改 `volatile` 并考虑临界区保护；`DEBUG_UART_SendString()` 是轮询等待 TXE，同样禁止在中断里调用（第 9 节第 3 条）。复杂度明显上升。

| # | 维度 | 定时轮询（目标版） | 按键中断 EXTI |
|---|---|---|---|
| 1 | 检测触发 | 定时器每 10ms 一次，与按键无关 | 引脚边沿，仅按键时发生 |
| 2 | 读引脚位置 | 主循环 `KEY_Tick()` → `KEY_ReadPins()` | ISR 置标志，或 ISR 直接读 |
| 3 | 消抖实现 | 状态机连续 3 拍确认，自然完成 | ISR 内无法完成，需另配定时器回读 |
| 4 | 时间基准 | 必须有，由 TIM3 提供 | 表面上不需要，实际消抖仍需要 |
| 5 | 空闲开销 | 每 10ms 读 5 路引脚 + 跑 5 个状态机 | 零 |
| 6 | 响应延迟 | 最坏 30ms（消抖）+ 一个主循环圈 | 边沿到 ISR 为微秒级，但确认仍需 30ms |
| 7 | 多键同时按下 | 一次位图读齐，5 个状态机独立处理，各报一次 | 需多条线/向量，共享向量时逐个判别 |
| 8 | 引脚号重复 | 无影响，位带读 IDR 直接区分端口 | 受限，同一 EXTI 线只能选一个端口 |

| 10 | ISR 复杂度 | 只置一个标志，约 5 行 | 多线判别 + 清标志 + 抖动处理 |
| 11 | 共享数据 | 全在主循环，无需 volatile / 临界区 | 需 volatile 与临界区保护 |
| 12 | 低功耗唤醒 | CPU 需保持运行以维持节拍 | 可在停止模式下由按键唤醒 CPU |
| 13 | 行为可复现性 | 采样间隔固定，去抖时间恒定 | 依赖边沿与抖动分布，需额外定时确认 |
| 14 | 本工程适用性 | 可行，已采用 | 5.2 的引脚冲突使其无法独立完成 |

## 7. 各自的适用场景

这里不否定 EXTI，两种方式有各自的适用范围。

**定时轮询适合**：按键数量多；引脚号存在重复或分散在多个端口；需要统一消抖、长按、组合键逻辑；主循环本来就在持续运行；要求行为与系统负载无关。本工程全部符合。

**按键中断适合**：按键少且引脚号互不重复；系统需要进入低功耗停止模式，靠按键唤醒 CPU；按键事件极稀疏，不值得维持周期节拍；只关心「有变化」而不关心长按/连发（例如旋钮编码器的边沿计数）。

**本工程的判断**：72MHz 全速运行，没有低功耗唤醒需求；5 颗键里有两个 Pin15（PD15 / PA15）落在同一条 EXTI 线上；需要 30ms 统一消抖和长按不连发。因此轮询是唯一能完整覆盖需求、且不引入额外机制的方案。

如果以后 PCB 改版把按键挪到互不重复的引脚号，并且确实需要按键唤醒，可以重新评估；即便如此，消抖环节仍建议保留定时扫描，EXTI 只承担唤醒。

## 8. 目标版里「中断」的准确用法与约束

1. 唯一的中断服务程序是 `TIM3_IRQHandler()`（`timer.c`），属于时基中断，不属于按键检测。
2. 它必须保持只做两件事：清 TIM3 更新标志、置 `s_tick_10ms = 1`。不得加入读引脚、状态机、队列、串口发送。
3. `KEY_Tick()` 与 `KEY_Pop()` 在主循环同一上下文调用；不得在中断里调 `KEY_Pop()`。
4. `DEBUG_UART_SendString()` 是轮询等待 TXE，只能在主循环调用。
5. 初始化顺序固定为 `NVIC_Configuration()` → `DEBUG_UART_Init()` → `KEY_Init()` → `TIM3_10ms_Init()`；其中 `NVIC_Configuration()`（NVIC 分组 2）必须早于 `TIM3_10ms_Init()`，否则中断优先级配置不生效。
6. 按键部分不编写任何 EXTI 配置、不使能 `AFIO` 的 EXTI 映射、不新增中断向量。
7. 采样每 10ms 一次、取事件每主循环圈一次，两个节奏不要合并。

## 9. 常见疑问

**有 TIM3 中断，为什么还说不是中断检测？**
「中断检测」指的是按键动作触发中断（EXTI）。TIM3 中断由定时器溢出触发，发生与否和按键无关，它提供的是时间基准。按键的识别动作全部在主循环完成，所以归类为扫描。

**轮询是不是主循环每圈都在读引脚，很费 CPU？**
不是。只有 `Tick_10ms_Take()` 返回 1 时才调 `KEY_Tick()`，即每 10ms 一次。每次的工作量是 5 次位带读 + 5 个 `switch` 状态转移，占用相对 72MHz 可忽略。主循环其余圈只做一次 `KEY_Pop()` 判空。

**扫描会不会漏掉很短的按键？**
会，这是设计预期。短于 30ms 的按下（含抖动）不满足连续 3 拍确认，会被过滤掉。原工程的有效消抖窗口同样是 30ms。若需要捕捉极短脉冲，应调整 `KEY_DEBOUNCE_TICKS`，而不是改成 EXTI。

**响应会不会明显变慢？**
从按下到事件入队最坏 30ms，加上取出与分发的一圈主循环时间。人机交互按键通常要求 20~50ms 消抖，这个量级无感知；而且延迟是固定的，不随系统负载漂移。

**能不能两种混用？**
技术上可以，但本工程不建议。若混用，合理分工是：EXTI 只用于低功耗唤醒，按键识别仍由 10ms 扫描完成；否则会出现两套状态来源，队列与状态机的并发处理都要重做。

**以后想加长按连发怎么办？**
在 `KEY_Tick()` 的状态机里给 `KEY_ST_PRESSED` 增加计时与重复间隔即可，不需要引入 EXTI。目标版当前明确不做长按连发、组合键、按键 LED 控制与接收中断（`KEY重构操作建议.md` 第 9 节第 9 条）。
