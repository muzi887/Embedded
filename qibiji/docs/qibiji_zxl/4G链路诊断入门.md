# 4G 链路诊断入门：从 CSQ 说起

本文围绕蜂窝网络、4G 这条链路展开，从基站、模组、CSQ/RSSI 等基础概念讲起，目标是看懂一条 4G 链路是怎么建立的、出问题时从哪看起，并结合本工程（qibiji_zxl，USR-WH-LTE-7S1 模块）实际踩过的现象说明。

---

## 一、先建立全局图景

### 1.1 什么是"蜂窝"

"蜂窝"（Cellular）指的是网络拓扑：运营商把一片区域划分成许多相邻的**小区（Cell）**，每个小区由基站（在 4G 里叫 eNodeB）的一个扇区覆盖。这些小区拼在一起形状类似蜂窝，所以叫蜂窝网络（一座基站通常带多个扇区、对应多个小区，精确关系见 1.3）。

为什么要分小区而不是用一个大功率基站全覆盖：

- 频率资源有限，复用频率才能在有限频段内容纳海量用户；
- 距离越远信号衰减越快，小小区能保证终端收到的信号强度足够；
- 终端可以在小区之间**切换（Handover）**，移动时保持连接。

4G（LTE）、5G、GSM、WCDMA 都是蜂窝网络，区别主要在空口技术和频段。本工程用的是 4G。

### 1.2 一条 4G 链路的角色

```
MCU ──UART──► 4G 模块 ──射频──► 基站(eNodeB) ──► 运营商核心网 ──► 公网 ──► MQTT 服务器
```

- MCU 只负责发 AT 命令和收数据，不直接碰射频；
- 4G 模块负责 SIM 鉴权、小区搜索、注册、建立数据链路、收发 IP 包；
- 基站和运营商网络是"黑盒"，MCU 能观察到的只是模块回给的状态。

所以链路出问题时，MCU 看到的表象往往是"LINKA 变低"或"AT 无响应"，根因可能在模块、在信号、在 SIM、在运营商侧，需要用 AT 命令逐层排查。

### 1.3 基站与模组：链路两端的两个角色

"基站"和"模组"是这条链路上最容易被混为一谈、但实际上分别在两端的两个关键角色。先把它们分清，后面讲搜网、注册、信号才不会乱。

#### 基站（Base Station）

基站在网络侧，是运营商花钱部署的设备，通常架在铁塔或楼顶上。它在不同代际的蜂窝网络里名字不同：

| 代际俗称 | 正式技术名（空口） | 数据业务 | 基站名称 | 含义 |
|---|---|---|---|---|
| 2G（俗称 2.5G 的数据部分） | GSM | **GPRS**（General Packet Radio Service，分组数据业务）→ EDGE | BTS（Base Transceiver Station） | 基站收发信机 |
| 3G | WCDMA / CDMA2000 / TD-SCDMA | — | Node B | — |
| 4G | **LTE**（Long Term Evolution，长期演进） | LTE 本身就是全 IP | **eNodeB** | evolved Node B，演进型 Node B |
| 5G | NR（New Radio） | — | **gNodeB** | next generation Node B |

要点：

- **LTE 就是 4G 的正式名字**，两个词指同一件事。模块日志、AT 回包里出现 LTE，和说"4G 在线"是一个意思；
- **GPRS ≠ 4G**。GPRS 是 2G GSM 时代的分组数据技术，跑在 2G 网上；本工程的链路跑的是 LTE；
- 工程里 `gprs_*.c/.h` 的文件名、口头说的"GPRS 模块"，只是从 2G 时代沿袭下来的习惯叫法，**模块实际注册的是 LTE（4G）网络**，和真正的 GPRS 无关；
- 查注册状态时命令分代：`AT+CREG?` 是 2G/GSM 的注册查询，`AT+CEREG?` 是 LTE/EPS 的注册查询（本工程属于后者，见第五节）。

基站的核心职责：

- **射频收发**：把核心网送来的 IP 数据调制到空口发射出去，把终端发来的上行信号解调回 IP 数据；
- **资源调度**：把时频资源块（RB）动态分配给各个在线终端，决定谁在什么时候用哪段频率；
- **空口协议终结**：物理层（PHY）和数据链路层（MAC/RLC/PDCP）在基站侧终止，再往上交给核心网；
- **移动性管理**：终端移动时，基站决定何时把它切换（Handover）到相邻小区；
- **广播系统消息**：周期性广播小区配置（MIB/SIB），让附近的终端能搜到自己。

一个容易忽略的细节：**"基站"和"小区"不完全等同**。一座 eNodeB 通常带 3 个扇区（三叶草布局）覆盖 360°，每个扇区就是一个独立的小区，有自己的频点和小区标识。所以一座基站可以管多个小区。模组搜网时锁定的是"某个小区"，而不是笼统地"连上某座基站"。

#### 模组（Module）

模组在终端侧，是焊在我们自己板子上的设备。本工程用的 **USR-WH-LTE-7S1**（有人物联网，DIP 23pin）是一个 4G **LTE Cat.1** 通信模组。

模组内部高度集成，把一整套蜂窝通信需要的东西都塞进了一个芯片模组里：

- 射频前端：功放（PA）、低噪声放大器（LNA）、滤波器；
- 基带芯片：负责物理层的调制解调、编解码；
- 完整协议栈：从空口物理层一直到 IP 层，相当于把一个"简化版手机的通信部分"封装起来；
- AT 命令解析器：对外提供标准的 AT 命令接口。

对 MCU 来说，模组是一个**黑盒**：MCU 只通过 UART 发 AT 命令、收数据，模组吐出来的已经是解调、解析、跑完协议栈之后的结果——比如 `+CSQ: 22,99` 这个信号读数、`+CEREG: 0,1` 这个注册状态、或者一段已经去封装的 IP 数据。MCU 不需要、也无法直接操作射频和基带。

**为什么本项目选 Cat.1**。LTE 终端按 3GPP 定义分不同的 Category（类别），类别决定了峰值速率、天线数等能力等级。常见的几档：

| 类别 | 下行峰值 | 上行峰值 | 典型用途 |
|---|---|---|---|
| **Cat.1** | 10 Mbps | 5 Mbps | 中低速物联网：抄表、远程控制、状态上报 |
| Cat.4 | 150 Mbps | 50 Mbps | 手机、移动热点等高速率场景 |
| Cat.M1 / NB-IoT | 1 Mbps 以下 | — | 极低速率、低功耗广域（LPWA），需运营商专门部署 |

本工程的闸门控制器只做开度/状态上报和开关命令下发，单次数据量也就几百字节到几 KB，Cat.1 的速率绰绰有余。相比 Cat.4，Cat.1 成本更低、功耗更小，而覆盖能力与 Cat.4 相当（都走运营商 4G 主频段，不像 NB-IoT 那样依赖专门的网络部署），是这类"小数据、长连接、广覆盖"场景的主流选择。市面上现在大量出货的是 **Cat.1 bis**（Cat.1 的低成本精简版，3GPP Rel-13 引入），速率与 Cat.1 同档但芯片成本更低；本模块按官方规格标注为 Cat.1，对本项目的能力完全够用。

需要强调一点：**Cat.1 不等于"信号差"或"速率不够"**。本工程遇到的弱覆盖、注册失败是空口覆盖问题（基站距离/遮挡/干扰），和 Cat 类别无关——在同一位置换成 Cat.4，信号也不会变好。选 Cat.1 是成本和功耗的权衡，不是信号上的妥协。

术语上要注意两点：

1. 工程里"模组"和"模块"经常混用，本文档里说的"4G 模块"指的就是这个通信模组，不是别的东西；
2. **模组 ≠ 基站**。模组是终端侧（我们的设备），基站是网络侧（运营商的设备）。是模组主动去搜索、锁定基站，基站只做广播，不会主动去找某个特定模组。

#### 两者的接口：Uu 空口

模组和基站之间的无线接口叫 **Uu 接口**（俗称空口）。本工程调试中遇到的所有"信号"问题——RSSI 低、搜不到网、注册失败、模块反复重启——本质都是这条 Uu 空口上的事情。模组测到的 RSSI/RSRP 反映的就是空口质量；模组反复重启重连，是它在尝试重新和基站建立空口连接。

调试时能动手的是**终端侧**：模组固件、天线、馈线、SIM 卡、供电；基站侧属于运营商，只能通过运营商确认覆盖和参数，自己改不了。这也是为什么弱覆盖问题往往只能靠"等网络侧响应"或调整安装位置/天线来解决，而不是靠改代码。

## 二、CSQ 是什么

### 2.1 命令与回包

`AT+CSQ` 是 3GPP TS 27.007 定义的标准 AT 命令，全称 Signal Quality（信号质量）。模块回包格式固定：

```
AT+CSQ
+CSQ: <rssi>,<ber>
OK
```

本工程日志里的典型回包：

```
usr.cn#
+CSQ: 22,99
OK
```

### 2.2 两个字段

**rssi**：Received Signal Strength Indicator，接收信号强度指示。取值范围：

| rssi | 含义 |
|---|---|
| 0 | ≤ -113 dBm（基本无服务） |
| 1 ~ 31 | 有效信号，数值越大越强 |
| 99 | 未知或不可测（Not known / Not detectable） |

近似换算公式：

```
dBm = -113 + 2 × rssi
```

例如 rssi=22 → -113 + 44 = **-69 dBm**，属于正常信号。

**ber**：Bit Error Rate，误码率。取值 0~7（7 是最高误码率档）或 99（未知）。4G 时代大多数模块直接回 99，这个字段基本不看了。

### 2.3 rssi=99 不等于"没有信号"

这是最容易被误读的一点。3GPP 对 99 的定义是"未知或不可测"，可能的原因包括：

- 模块还没完成射频初始化，正在启动；
- 正在搜网，还没锁定任何小区；
- 注册被拒绝，模块在反复尝试；
- 天线未接或接触不良；
- 极少数情况下是模块固件的 bug 或查询时机不对。

所以 `+CSQ: 99,99` 只能说明"此刻模块没给出有效读数"，**不能直接下结论说没信号**，要结合注册状态（见第四、五节）和时序一起看。

## 三、RSSI：信号强度到底测的是什么

"信号好不好"几乎所有判断都从 RSSI 起步，而它恰恰是最容易被误读的指标，这一节讲清它物理上到底测的是什么。

### 3.1 定义

RSSI = Received Signal Strength Indicator，接收信号强度指示。它表示**接收机在测量带宽内测到的总接收功率**，单位 dBm。关键在于"总功率"——它不是某个特定信号的功率，而是天线口进来的、落在测量带宽内的所有能量之和，包括：

- 服务小区（当前正在连的基站）发来的信号；
- 同频或邻频的其它基站信号；
- 环境噪声与外界干扰。

所以 RSSI 是一个"宽带总量"，不是"有用信号量"。这个区别决定了它的一切局限性。

### 3.2 dBm 是对数刻度，不能按线性读

读 RSSI 数值时第一个要建立的直觉：dBm 是相对于 1mW 的分贝，定义为

```
dBm = 10 × log10(功率 / 1mW)
```

- 1mW = 0 dBm；
- 0.1mW = -10 dBm；
- 1μW = -30 dBm；
- 我们读到的 -69 dBm ≈ 1.26×10⁻⁷ mW = 0.126 nW，是极小的功率。

因为是对数，**数值差 3dB 就代表功率差一倍**（+3dB 翻倍，-3dB 减半），差 10dB 代表功率差 10 倍。所以 rssi=22（-69dBm）和 rssi=17（-79dBm）之间，看着只差 5 个数，实际接收功率差了约 10 倍。判断信号好坏要看 dBm 差多少，不能用"差几个 rssi 数"去线性估计。

### 3.3 为什么 4G 时代 RSSI 不够用了

RSSI 是 2G（GSM）/3G（UMTS）时代的主力指标，那时候好用是有原因的：GSM 一个载频 200kHz，基本就是一个用户在用，整个信道的功率约等于服务小区的信号功率，RSSI 测出来就近似于"我收到的基站信号有多强"。

到了 4G（LTE）情况变了。LTE 用 OFDMA，一个 20MHz 带宽里同时有很多用户复用不同的资源块（RB）。这时 RSSI 测的是**整个 20MHz 的总功率**，里面混了属于我的参考信号和数据、同小区其他用户的信号、邻小区的同频干扰、以及噪声。RSSI 数值高，可能是我自己的信号强，也可能是干扰强。单看 RSSI 已经无法判断"我的信号到底好不好、能不能解调"。

因此 3GPP 为 LTE 定义了更精细的三个指标：

| 指标 | 全称 | 测的是什么 | 工程含义 |
|---|---|---|---|
| **RSRP** | Reference Signal Received Power | 只测小区特定参考信号（CRS）的平均功率 | 真正的"有用信号强度"，判断覆盖好不好主要看它 |
| **RSRQ** | Reference Signal Received Quality | N×RSRP / RSSI，信号占总功率的比例 | 反映信号纯净度，类似信噪比，判断干扰大不大 |
| **SINR** | Signal to Interference plus Noise Ratio | 有用信号 /（干扰 + 噪声） | 最直接反映解调能力，决定速率和稳定性 |

数量级上，RSRP 通常比 RSSI 低 6~20dB（RSSI 是整个带宽求和，RSRP 是单个参考信号资源单元的功率），但没有固定换算关系，取决于带宽和小区负载。

### 3.4 为什么我们的模块还在用 AT+CSQ 回 RSSI

3GPP TS 27.007 的 `AT+CSQ` 是 GSM 时代就定下的 legacy 命令。绝大多数 4G 模块为了兼容老的 AT 框架和上位机软件，仍然实现它，并把测量结果映射到 0~31 的 rssi 范围返回。模块内部实际测的是 RSRP（或全带宽功率），输出时套了一层 rssi 的壳。这就是为什么 `-113 + 2×rssi` 只能当工程近似——它不是模块真实测到的精确 dBm，而是为了兼容旧接口做的映射。判断"信号好不好"够用，拿去做精确的链路预算或覆盖评估就不够了。

### 3.5 工程上怎么用 RSSI

在没有 RSRP/SINR 可读的情况下（本工程的 USR-WH-LTE-7S1 就属于这种，`AT+CSQ` 是唯一的信号读数），按 rssi 数值大致分档：

| rssi | 约 dBm | 工程判断 |
|---|---|---|
| ≥ 20 | ≥ -73 | 信号好，稳定连接无压力 |
| 14 ~ 19 | -85 ~ -75 | 可用，城区正常水平 |
| 12 ~ 13 | -89 ~ -87 | 边缘，偶发掉线需留意 |
| ≤ 11 | ≤ -91 | 弱覆盖，容易注册失败或反复重启 |
| 99 | 不可测 | 见 §2.3 |

这张表是经验分档，不是 3GPP 标准阈值，实际表现还受干扰、多径、模块灵敏度影响，只能作为初筛。分档按 rssi 每 +1 对应 +2dBm 换算，相邻档位之间出现 2dB 间隙（如 -74、-76）是 rssi 离散化的正常结果，不代表存在信号盲区。

### 3.6 RSSI 数值好，不代表能上网

这是最关键的一条认知。RSSI 是宽带总功率，**会被干扰和噪声抬高**。如果现场有强干扰源（同频段的其它设备、或基站故障导致的异常发射），RSSI 读数可能很好（比如 rssi=25），但有用信号被干扰淹没、SINR 极差，结果就是 CSQ 看着不错，却注册不上、或注册上了速率极低。反过来，RSSI 不算很高（比如 rssi=14，-85dBm），但干扰小、SINR 好，链路照样稳定。

所以排查时的分流原则：

- RSSI 差（≤11 或大量 99）→ 优先查天线、馈线、现场覆盖；
- RSSI 好但注册不上 → 不要死磕信号，去查 SIM、干扰、运营商侧（见下一节链路建立过程与 AT 命令表）；
- 最可靠的是**结合时序看分布**：本工程案例里 34 次查询只有 3 次有效值、其余全 99，这种"偶发好、持续差"的分布比单个数值更能说明问题（见第六节案例）。

## 四、一条链路建立的完整过程

理解这个过程，才能知道 CSQ 卡在哪个阶段。

```
阶段 0  模块上电
          │  打印 "WH-LTE-7S1" 等启动 banner
阶段 1  识别 SIM 卡
          │  AT+ICCID 能读到卡号 → SIM 物理接口正常
阶段 2  搜索小区并注册
          │  AT+CREG? / AT+CEREG? 回 1 或 5 → 注册成功
          │  回 2 → 搜网中；回 3 → 被拒绝
阶段 3  附着到分组域（PDP 激活）
          │  AT+CGATT? 回 1 → 附着成功，可以收发 IP 包
阶段 4  建立 MQTT 会话
          │  模块连服务器，LINKA（PC5）拉高
阶段 5  稳态收发
          │  心跳、属性上报正常
```

关键点：**每一步都是上一步的前提**。SIM 没识别就不可能注册；没注册就不可能附着；没附着 MQTT 就连不上。所以排查要从前往后，不能跳步。其中**阶段 2（搜索小区并注册）是信号质量的卡点**：CSQ/RSSI（见第二、三节）决定了这一步能否成功；如果信号读数不差却始终卡在阶段 2，方向就要从"信号"转向"SIM / 运营商侧"。

## 五、排查时要看的几条 AT 命令

| 命令 | 看什么 | 典型正常回包 | 典型异常回包 |
|---|---|---|---|
| `AT+ICCID` | SIM 是否被识别 | `+ICCID: 8986...`（一串数字） | `ERROR` 或空 |
| `AT+CSQ` | 信号强度读数 | `+CSQ: 16~31,99` | `+CSQ: 99,99` |
| `AT+CREG?` | GSM 注册状态 | `+CREG: 0,1`（已注册本地） | `+CREG: 0,2`（搜网中）或 `0,3`（拒绝） |
| `AT+CEREG?` | LTE/EPS 注册状态 | `+CEREG: 0,1` | `+CEREG: 0,3` |
| `AT+CGATT?` | 分组域附着状态 | `+CGATT: 1` | `+CGATT: 0` |
| `AT+MQTTSTAT?`（或厂家命令） | MQTT 会话状态（现场手动排查用） | 已连接 | 未连接 |

> 本工程代码不发 `AT+MQTTSTAT?`，而是靠模块的 LINKA 指示引脚（PC5）驱动状态机、配合 `gprs_is_ready()`（进入 ST_NORMAL）判断 MQTT 是否在线；上表列出它仅作为现场手动排查的备用手段。

**工作模式与网络参数类指令**（USR 原厂标准，本工程状态机探询阶段会周期性发出，用于确认模块配置未被改动）：

| 命令 | 类别 | 说明 | 取值 / 含义 |
|---|---|---|---|
| `AT+WKMOD` | 通用指令 | 查询 / 设置工作模式 | `NET`（透传）、`MQTT`、`SMS` 等；`MQTT,NOR` 为 MQTT 正常分发模式 |
| `AT+HEARTEN` | 心跳包指令 | 查询 / 设置心跳包使能 | `ON` / `OFF` |
| `AT+SOCKASL` | 网络参数指令 | 查询 / 设置 Socket A 连接方式（长 / 短连接） | `LONG` / `SHORT` |
| `AT+SOCKALK` | 网络参数指令 | 查询 Socket A 连接状态 | 只读，返回连接与否 |

本工程实测值：`+WKMOD: MQTT,NOR`、`+HEARTEN: OFF`（模块自带心跳关闭，应用层用自己的 `up/sys/heartbeat` 接管）、`+SOCKASL: LONG`；`AT+SOCKALK` 代码不发，仅作现场手动排查用。

**CREG/CEREG 状态字段（第二个数）的通用语义**：

- 0：未注册，模块没有在搜网；
- 1：已注册，归属网（本地）；
- 2：未注册，正在搜网；
- 3：注册被拒绝；
- 4：未知；
- 5：已注册，漫游。

看到 `3`（拒绝）通常是 SIM 欠费、未激活、或运营商限制；看到长期 `2`（搜网中）通常是信号弱、频段不匹配、或天线问题。

**CEREG 完整回包（五字段格式，本工程实测）**：

```
+CEREG: <mode>,<stat>,"<TAC>","<CI>",<AcT>
实测：+CEREG: 3,1,"e30f","01127638",7
```

- `mode`=3：URC 上报模式——注册状态一变化模块就主动推送这条，不等查询；
- `stat`：第二个字段，语义就是上表（实测 1 = 已注册归属地网络）；
- `"e30f"`：TAC 跟踪区码；`"01127638"`：小区 ID（当前驻留的基站）；
- `AcT`=7：接入技术 E-UTRAN，即 LTE——本模块 Cat.1 走的正是这个。

## 六、本工程实际遇到的现象与分析

以下是本次调试中真实出现过的情况，作为上述知识的应用案例。

### 6.1 现象

- 模块反复打印启动 banner（`WH-LTE-7S1`），间隔 10~77 秒不等；
- `pc4=0 pc5=0`（LINKA 始终为低），MQTT 从未建链；
- 34 次 `AT+CSQ` 查询中只有 3 次返回有效值（20~23），其余全是 99；
- MCU 侧按设计每 60 秒判离线、每 5 分钟硬复位 4G 模块，但**两次硬复位都没能救活链路**；
- 最后在没有任何外部干预的情况下，模块自己注册成功，链路恢复并稳定运行 10 分钟以上。

### 6.2 分析过程

对照第四节的链路阶段，本次故障卡在**阶段 2（搜索小区并注册）**：SIM 卡已识别（阶段 1 通过），但始终进不了注册成功。下面按第五节的检查表逐项排除根因：

- `AT+ICCID` 能读到 `89861124204085195798` → SIM 卡物理识别正常，排除卡没插好；
- `+CSQ` 偶发能到 22（-69dBm）→ 射频和天线**至少有时能工作**，排除彻底的硬件损坏；
- 两次硬复位都没用 → 复位不是根因，排除"模块卡死需要复位"；
- 信号好的时候（链路恢复后 MQTT 持续发射）模块不重启 → 排除供电不足（发射电流最大，若供电跌落会在此时复现）；
- 离线探询每 5 秒灌 AT，恢复时仍在灌，照样注册成功 → 排除探询干扰。

剩下的合理解释是：**现场信号处于弱覆盖边缘，模块每次启动尝试附着都失败，失败后自行重启重试，二十几次后某一次正好赶上网络侧响应，注册成功并稳定。** 这是模块自身的重注册策略在起作用，不是 MCU 代码的问题，也不是硬件故障。

### 6.3 结论

代码侧不需要修改。但这个案例说明了两个通用原则：

1. **CSQ 的瞬时值没有意义，要看一段时间的分布**。偶尔的 22 说明链路有通的可能性，持续的 99 说明当前不稳定，两者要结合看；
2. **看门狗/硬复位对"网络侧不可达"这类问题无能为力**。复位只能解决"模块自身软件卡死"，解决不了信号弱或 SIM 被拒。遇到复位无效的情况，要往信号、SIM、运营商方向查，而不是调复位间隔。

### 6.4 AT 回包实测盘点：LINK=0 时的全链路体检（2026-11-25）

现象：bootloader 阶段 LINKA 一直为 0，设备"在线"始终不亮。用 AT 命令把链路从 SIM 到服务器配置逐层查了一遍，七条回包如下：

| AT 应答 | 字段解读 | 结论 |
|---|---|---|
| `+ICCID: 89861124204085195798` | SIM 身份码（出厂写入的唯一编号），前缀 8986 = 中国电信号段 | 卡在位可读；此前 `+CME ERROR:58` 只是问得太早（模块未就绪），不是卡的问题 |
| `+CSQ: 15,99` | rssi=15 ≈ -113+2×15 = **-83 dBm**（中等偏好），ber=99 为惯例占位值 | 天线、射频侧正常 |
| `+WKMOD: MQTT,NOR` | MQTT 模式 + 正常运行模式 | 模块上电按存储配置**自动**去连 MQTT 服务器，MCU 一条命令都不用发——也解释了为什么 bootloader 不参与连接 |
| `+MQTTCID: dev001` | MQTT 客户端 ID，服务器靠它区分设备、推送下发 | 与 EEPROM 里的 dk=dev001 配套一致 |
| `+SOCKASL: LONG` | Socket 长连接（连上后一直保持） | MQTT 本就要求长连接，配套配置 |
| `+CEREG: 3,1,"e30f","01127638",7` | 已注册归属地网络（1），TAC `e30f`，小区 ID `01127638`，接入技术 7=E-UTRAN（LTE） | **注网成功**——排除卡、频段问题；LINK 一直为 0 期间它就是 1 |
| `+MQTTSVR: www.huanghe-ceshi.top,59165`（URC） | 这条**没发过命令**，是模块主动推送：报出自己的 MQTT 服务器配置 | 顺带证明模块→MCU 的推送链路（PA3→DMA→环形缓冲）畅通 |

七条合起来的故事：卡正常 → 射频正常 → 模块按 MQTT 长连接模式自动工作 → 身份与服务器配置齐备 → 网络已注册 → 但 LINK=0 ⇒ **卡在最上层"连服务器"**，而这一层唯一的外部依赖就是服务器本身——服务器关闭，配置再对也连不上。

结论三条：

1. **根因**：自建服务器关闭 → MQTT 连不上 → LINKA 保持低电平。LINKA 语义由此实测确认为"**已连接 MQTT 服务器**"——CEREG 注册成功期间它仍为 0 就是证据（呼应第八节"LINKA ≠ 信号好"）；
2. 阶段状态：USART 收发双向 + 4G 清单（点火 / 命令通道 / LINK / online / PD13 指示灯）**全部通过**；
3. bootloader 侧零改动收官。

## 七、排查顺序建议（按链路阶段由前到后）

排查顺序与第四节的链路阶段一一对应，从物理层往上走，卡在哪一步就查哪一步，不要跳步：

**阶段 0（上电）—— 物理层**
- 模块供电是否稳定（本工程模组主电源 3.4~4.2V，与 MCU 3.3V 不是同一路）；
- 天线是否拧紧、馈线是否接对；
- 能否收到启动 banner（`WH-LTE-7S1`）。完全收不到 → 查供电、固件、串口接线。

**阶段 1（SIM 识别）**
- `AT+ICCID` 有无回包、卡号是否合法；无回包 → 查 SIM 卡是否插到位、卡座接触是否良好。

**阶段 2（搜网 + 注册）—— 信号与注册的卡点**
- `AT+CSQ` 连续查几十次，统计有效值（rssi∈[1,31]）比例：几乎全 99 → 查天线 / 馈线 / 现场覆盖；
- `AT+CREG?` / `AT+CEREG?`：长期 `2`（搜网中）→ 信号弱或频段不匹配；`3`（被拒）→ 往下查 SIM 权限；
- 信号读数不差却始终注册不上 → 不要死磕信号，转向 SIM / 干扰 / 运营商侧（见 3.6）。

**阶段 3~5（附着 + MQTT + 稳态）**
- `AT+CGATT?` 是否附着；LINKA（PC5）是否拉高、`gprs_is_ready()` 是否为 1；
- 已附着但 MQTT 连不上 → 查 APN 配置、服务器地址 / 端口、MQTT 凭据。

**跨阶段：SIM 权限与运营商侧**
- 物联卡常见限制（APN 白名单、定向流量、禁止某频段、欠费停机）需要运营商侧确认，自己改不了。

## 八、几个容易混淆的概念

- **CSQ ≠ 注册状态**。CSQ 只给信号强度读数，注册成功与否要看 CREG/CEREG。信号好但注册被拒是可能的（如 SIM 欠费）。
- **LINKA 拉高 ≠ 信号好**。LINKA（本工程的 PC5）反映的是 MQTT 会话状态，不是射频信号。LINKA 低不一定是信号问题，也可能是服务器断连。实测证据见 6.4：CEREG 注册成功期间 LINKA 仍为 0，根因是服务器关闭。
- **rssi=99 ≠ 没信号**。99 是"不可测"（见 2.3），要结合时序和注册状态判断。
- **RSSI 数值好 ≠ 能上网**。RSSI 是宽带总功率，会被干扰和噪声抬高；真正决定能否解调的是 SINR。详见 3.6。
- **重启次数 ≠ 故障严重程度**。模块在弱覆盖下反复重启是它自己的重试机制，重启本身不是 bug，要看重启后能否最终稳定注册。
- **基站 ≠ 模组**。前者是运营商部署的网络侧设备，后者是焊在自己板上的终端侧设备；弱覆盖、搜不到网、注册失败是两者之间 Uu 空口的问题，能动手改的只有终端侧。详见 1.3。
