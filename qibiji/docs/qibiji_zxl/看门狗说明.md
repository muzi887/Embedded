# 看门狗说明

> 本文说明三个基础问题：什么是看门狗、什么时候需要看门狗、什么时候需要喂狗。文中的窗口数值、喂狗点均以本工程（`qibiji_zxl`，STM32F103 + IWDG）为准；具体落地代码见《看门狗重构操作建议.md》。

## 一、什么是看门狗

看门狗（Watchdog Timer，WDT）是一个**独立于 CPU 运行的递减计数器**。它不依赖主程序，只要芯片有电、看门狗已使能，它就自己往下数。

```
使能时装载初值 ──► 每个时钟周期 -1 ──► 数到 0 ──► 强制复位整个 MCU
                     ▲
                     └── 喂狗：在到 0 之前重新装载初值
```

三个关键特性：

1. **只能复位，不能中断**：STM32F1 的独立看门狗（IWDG）数到 0 后直接产生系统复位，不会先执行某个回调；
2. **一旦使能无法用软件关闭**：只能靠复位（或下次上电）恢复，所以调试时需要用 `DBGMCU_IWDG_STOP` 在断点处冻结；
3. **时钟源独立**：IWDG 由内部 LSI（30~60kHz，典型 40kHz）驱动，主时钟跑飞、PLL 失锁都不影响它继续计数。

### 名字的由来

英文 **watchdog**，直译"看门狗"。类比看家狗：程序正常时定时给它"喂食"，它就不叫；程序一旦挂了没人喂，它就"咬人"——把系统复位。

### 本工程的窗口计算

```c
#define WDG_PRESCALER  4u      /* 分频因子 = 4 × 2^4 = 64 */
#define WDG_RELOAD     1990u   /* 重装值（低 11 位有效） */

/* Tout = 64 × 1990 / f_LSI
 *   f_LSI = 40kHz → 3184ms（标称）
 *   f_LSI = 60kHz → 2123ms（最短，真正的设计上限）
 *   f_LSI = 30kHz → 4245ms（最长）
 */
```

也就是说：**同一份固件在不同芯片上，复位窗口可能是 2.1s，也可能是 4.2s**，设计时必须按最短的 2.1s 来约束，不能用标称值 3.18s 去卡边界。

## 二、什么时候需要看门狗

判断标准只有一条：**程序跑飞后，有没有人能马上按复位键？**

同时满足下面几条时，应该加看门狗：

| 条件 | 本工程情况 |
|---|---|
| 无人值守、长期在线 | 闸门控制器装在现场，通过 4G 远程管理 |
| 卡死后不会自愈 | 裸机大循环 + 大量阻塞等待，卡住就是永久卡住 |
| 失效后果严重 | 电机可能持续转动、限位失效、设备失联 |
| 现场无法人工干预 | 需要设备"自己复位爬起来" |
| 能说清最长阻塞时间 | 已知最长阻塞为 LCD 1.5s、GPRS 复位 1.5s、EEPROM 长写 |

### 不适合依赖看门狗的场合

| 场合 | 原因 |
|---|---|
| 开发调试阶段 | 断点停留超过窗口就复位，必须配合 `DBGMCU_IWDG_STOP` 冻结 |
| 用来看门狗"治"通信故障 | GPRS 掉线应走重连状态机，不该靠复位解决 |
| 最长阻塞时间说不清 | 先把阻塞拆开，再决定加不加狗 |
| 短生命周期、随时可断电 | 收益很小，反而增加调试成本 |
| 已经存在死循环喂狗 | 先删掉错误喂狗点，否则加了也是"假看门狗" |

> 看门狗的定位是**最后的兜底**，不是异常处理的替代品。它只能回答一个问题："程序还活着吗？"——回答不了"业务对不对"。

## 三、什么时候需要喂狗

喂狗（Feed / Kick the dog）就是调用 `IWDG_ReloadCounter()`，把计数器重新装载回 `WDG_RELOAD`，让它重新开始倒数。

核心原则：**只在能证明"系统仍在按预期执行"的位置喂，而不是随便找个地方喂。**

### 应该喂狗的位置

| 位置 | 证明什么 |
|---|---|
| 主循环完整跑完一轮（`while(1)` 循环头） | 调度、各模块 Tick、通信处理都没有卡死 |
| 已知合法长阻塞**内部按段**喂 | EEPROM 每字节 10ms、LCD 上电 1.5s、GPRS 复位 1s，不喂会被误判为死机 |
| 初始化阶段的关键长等待之后 | 让看门狗覆盖启动过程，而不是启动完才生效 |

### 绝对不能喂狗的位置

| 位置 | 后果 |
|---|---|
| 定时器 / 外部中断 ISR 里 | 主循环死了、中断还活着，故障被永久隐藏 |
| `delay_ms()` / `delay_us()` 内部 | 所有长延时自动免疫看门狗，等于没开 |
| 通信故障处理路径的死循环里 | 越出错越喂狗，正好掩护了错误 |
| 到处撒、越勤越好 | 喂狗点一多，审查不出"哪条路径其实没人喂" |

### 量化规则（本工程）

1. 喂狗周期取窗口的 1/2~1/3：主循环单轮 <20ms，远小于上限；
2. 任何**不喂狗**的连续执行路径必须 < 1.5s；
3. 单段阻塞超过 1.5s 必须拆段并在段间喂狗，不允许贴着 2.1s 设计；
4. 全工程喂狗点控制在 5 个以内，便于逐条审查；
5. 只允许两个名字出现：业务侧的 `WDG_Feed()` 和 `wdg.c` 内部的 `IWDG_ReloadCounter()`。

### 本工程的喂狗点

| 位置 | 阻塞时长 | 说明 |
|---|---|---|
| `main.c` 的 `while(1)` 循环头 | 一轮 <20ms | 主循环存活基线 |
| `AT24CXX_WriteOneByte()` 末尾 | 10ms/字节 | 32B 槽 320ms、四槽连续 1.28s |
| `LCD12864_Init()` 三段 500ms 之间 | 3 × 500ms | ST7920 上电需要 1.5s |
| `GPRS_4G_Init()` 复位脉冲后 | 500ms | 上电复位 |
| `GPRS_4G_Reset()` 复位脉冲后 | 1000ms | 运行期复位，由主循环调用 |

对应的判定链条是：**主循环不卡 → 正常喂狗；合法长阻塞 → 阻塞内部补喂；真卡死 → 没人喂 → 2.1~3.2s 后复位**。

## 四、常见误区

1. **"喂狗越勤越安全"**：错。喂狗的意义是证明路径执行到过这里，频率只要不超过窗口就够；喂得太勤反而让故障路径也能续命。
2. **"中断里也喂一下更保险"**：错。这是最典型的隐藏型故障，定时器还活着但主循环已死时，系统将永远不恢复。
3. **"把看门狗当复位按钮"**：错。通信超时、传感器异常应走业务状态机，频繁复位会丢数据、断开会话。
4. **"标称 3.18s，所以阻塞 3s 没问题"**：错。LSI 批次差异会让窗口缩到 2.1s，必须按最短值设计。
5. **"复位后 RAM 会清空"**：错。IWDG 复位不清 RAM，参数会保留，但业务仍应在上电时从 EEPROM 重新加载，不要依赖残留值做逻辑。

## 五、一句话总结

- **看门狗**：独立倒计时器，归零就复位，用于兜底"程序跑飞"；
- **什么时候需要**：无人值守、卡死不能自愈、失效后果严重、现场无法人工干预；
- **什么时候喂**：在主循环和已知长阻塞段内证明"我还活着"；中断里、延时里、故障循环里坚决不喂。
