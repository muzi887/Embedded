# 看门狗（IWDG）重构操作建议

> 系统级可靠性模块，独立于 EEPROM / GPRS / LCD 等业务模块。建议在 EEPROM 模块落地后立即接入：EEPROM 的长写（每字节约 10ms）与 LCD 上电等待（1.5s）、GPRS 复位脉冲（0.5~1.5s）是当前工程仅有的秒级阻塞路径，超时窗口必须逐一对齐。

## 原工程现状

- **驱动**：`HARDWARE/WDG/wdg.c` + `.h`，只有两个接口：`IWDG_Init(u8 prer, u16 rlr)`、`IWDG_Feed(void)`
- **窗口**：`main.c` 里 `IWDG_Init(4, 1990)`，标称 3180ms
- **喂狗点**：

| 位置 | 场景 |
|---|---|
| `main.c` 初始化后一次 + `while(1)` 循环头 | 主循环基线 |
| `24cxx.c` 的 `AT24CXX_WriteOneByte()` 末尾 | EEPROM 单字节写 10ms |
| `Dispaly.c` 三处 | 原工程 LCD 清屏/刷新 |
| `gprs_JSON.c` 第 280 行 | 长 JSON 拼装 |

原工程存在的问题：

1. 喂狗点散落在各业务文件里，没有统一窗口定义，改主频或 LSI 时无从下手；
2. `lcd12864.c` 的三段 `delay_ms(500)` 迁移到 zxl 时被注释为"本工程没有看门狗，拆分只为不超过 delay_ms 上限"，喂狗语义丢失；
3. zxl 的 `eeprom_drv.c` 删掉了 `IWDG_Feed()`，同时把单字节写等待改成了 `delay_ms(10); delay_ms(10);`（20ms/字节），连续写四个 32B 凭据槽就是 2.56s，已超过最坏情况窗口；
4. 没有任何"上次是否为看门狗复位"的记录，现场无法区分是掉电重启还是狗咬。

## 重构目标

1. **保留** IWDG（不换 WWDG），窗口沿用 `4 / 1990`，与原工程行为一致；
2. 喂狗点收敛为**两类**：主循环一次 + 显式长阻塞点，禁止在中断里喂狗；
3. 按**最坏 LSI = 60kHz** 的最短窗口（2123ms）约束所有单段阻塞，不允许贴着窗口上限设计；
4. 统一封装为 `WDG_Init()` / `WDG_Feed()`，窗口参数做成宏，便于后续调整；
5. 上电记录复位来源，串口就绪后打印，便于现场判读。

## 新增文件清单

| 文件 | 职责 | 来源 |
|---|---|---|
| `HARDWARE/WDG/wdg.h` + `.c` | IWDG 使能、喂狗、窗口宏、复位来源记录 | 从原工程 `HARDWARE/WDG/` 拷贝，函数收敛为 `WDG_Init/WDG_Feed`，类型统一 `uint8_t/uint16_t` |

> 不需要新增标准库文件：`STM32F10x_FWLib/src/stm32f10x_iwdg.c` 已在工程内（`OBJ/` 里有对应的 `.o`），`USER/stm32f10x_conf.h` 也已包含 `stm32f10x_iwdg.h`。
>
> **不要调用 `DBGMCU_Config()`**：`stm32f10x_dbgmcu.c` 不在 Keil 工程里，调用会报 `L6218E: Undefined symbol DBGMCU_Config`；且 STM32F1 的 `DBGMCU_CR` 只能由调试器写入，固件写它本来就不生效。调试冻结见 §6。
>
> `OBJ/` 下现存的 `wdg.o` 是早期编译残留，本次需要把新的 `HARDWARE/WDG` 目录加入 Keil 工程并 **Rebuild**，避免链接到旧对象。

## §1 wdg 模块（固定窗口 + 复位来源记录）

`wdg.h`：

```c
#ifndef __WDG_H
#define __WDG_H

#include "stm32f10x.h"   /* 提供 uint8_t / uint16_t，并引入 IWDG 寄存器定义 */

/*
 * 窗口配置：IWDG 时钟源为内部 LSI（数据手册 30~60kHz，典型 40kHz）
 *   分频因子 = 4 * 2^WDG_PRESCALER = 4 * 2^4 = 64
 *   Tout = 64 * 1990 / f_LSI
 *     f_LSI = 60kHz → 2123ms（最短，所有单段阻塞必须小于该值）
 *     f_LSI = 40kHz → 3184ms（标称，与原工程 main.c 的 3180ms 一致）
 *     f_LSI = 30kHz → 4245ms（最长）
 */
#define WDG_PRESCALER        4u
#define WDG_RELOAD           1990u
#define WDG_WINDOW_MIN_MS    2123u

/* 上次复位是否由 IWDG 引起（1=是）。main 在串口初始化完成后打印 */
extern volatile uint8_t g_wdg_reset_cause;

/* 使能 IWDG。注意：一旦使能，软件无法关闭，只能靠复位恢复 */
void WDG_Init(void);

/* 重装载 IWDG 计数器 */
void WDG_Feed(void);

#endif
```

`wdg.c` 完整源码：

```c
#include "wdg.h"

volatile uint8_t g_wdg_reset_cause = 0u;

/* 初始化独立看门狗：窗口 3.18s@40kHz LSI，最坏情况 2.12s */
void WDG_Init(void)
{
    /* 1) 先记录复位来源，再清标志；打印交给 main（此时串口可能还没初始化） */
    g_wdg_reset_cause = (RCC_GetFlagStatus(RCC_FLAG_IWDGRST) != RESET) ? 1u : 0u;
    RCC_ClearFlag();

    /* 2) 调试冻结说明：STM32F1 的 DBGMCU_CR 只能由调试器写入，固件调用
     *    DBGMCU_Config() 既无效，还会因工程未编译 stm32f10x_dbgmcu.c 而报
     *    L6218E。调试时在 Keil → Options for Target → Debug → Settings
     *    勾选 "Stop Watchdog Counters"，由调试器写该位。 */

    /* 3) 写保护 → 预分频 → 重装值 → 重装载 → 使能 */
    IWDG_WriteAccessCmd(IWDG_WriteAccess_Enable);
    IWDG_SetPrescaler(WDG_PRESCALER);
    IWDG_SetReload(WDG_RELOAD);
    IWDG_ReloadCounter();
    IWDG_Enable();
}

/* 喂独立看门狗 */
void WDG_Feed(void)
{
    IWDG_ReloadCounter();
}
```

> 与原工程接口的差异：`IWDG_Init(u8 prer, u16 rlr)` 的参数被固化为宏，调用方不再关心分频/重装值；`IWDG_Feed()` 改名为 `WDG_Feed()`。如果希望保留原接口，可在 `wdg.h` 里加一层 `#define IWDG_Feed() WDG_Feed()`，但本工程没有历史调用点，直接改名即可。

## §2 窗口与阻塞段预算

| 阻塞段 | 时长 | 距最坏窗口 2123ms 的余量 |
|---|---|---|
| 主循环单轮 | < 20ms | 充裕 |
| EEPROM 单字节写 | 10ms | 充裕 |
| EEPROM 一个 32B 凭据槽 | 320ms | 充裕 |
| EEPROM 连续写四个凭据槽（远程 config） | 1.28s | 约 0.84s（且每字节都会喂狗） |
| LCD12864 上电等待（三段 500ms） | 1.5s | 段间喂狗后每段 500ms |
| GPRS 上电复位脉冲 | 500ms | 段后喂狗 |
| GPRS 运行期复位（复位 1s + `GPRS_4G_Init` 0.5s） | 1.5s | 两个脉冲后各喂一次 |

**预算规则**：任何一条**不喂狗**的连续执行路径都必须 < 1.5s；允许介于 1.5s 与 2.1s 之间的路径只限于已在段中喂狗的阻塞函数。超过 2.1s 的路径视为设计缺陷，必须拆段。

> 注意：`delay_ms(u16)` 在 72MHz 下最大只能延时约 1864ms，单次长延时本来就必须拆段，这与看门狗窗口天然吻合。

## §3 喂狗点清单

| 位置 | 喂狗方式 | 理由 |
|---|---|---|
| `main.c` 的 `while(1)` 循环头 | `WDG_Feed();` | 主循环存活基线，与原工程一致 |
| `AT24CXX_WriteOneByte()` 末尾（`delay_ms(10)` 之后） | `WDG_Feed();` | 单字节 10ms，长写会累积到秒级 |
| `LCD12864_Init()` 三段 500ms 之间 | 每段后 `WDG_Feed();` | ST7920 上电需 1.5s |
| `GPRS_4G_Init()` 复位脉冲 500ms 后 | `WDG_Feed();` | 上电复位阻塞 |
| `GPRS_4G_Reset()` 复位脉冲 1000ms 后 | `WDG_Feed();` | 运行期复位阻塞，且从主循环调用 |

### 3.1 main.c

在 `DEBUG_UART_Init()` 之后、`KEY_Init()` 之前启动（此时初始化耗时只有微秒级，晚启动可以保证串口能打印复位来源）：

```c
#include "wdg.h"

NVIC_Configuration();
DEBUG_UART_Init();
WDG_Init();                     /* 新增：3.18s@40kHz，最坏 2.12s */
WDG_Feed();
if (g_wdg_reset_cause != 0u)
    DEBUG_UART_SendString("reset cause: IWDG\r\n");

KEY_Init();
delay_init();
/* 其余初始化保持不变 */
```

主循环只在**循环头**喂一次，不要挂在 `Tick_10ms_Take()` 分支里：

```c
while (1)
{
    WDG_Feed();                  /* 新增：每轮一次，不随节拍条件跳 */

    if (Tick_10ms_Take())
    {
        KEY_Tick();
        LCD_BACKLIGHT_Tick();
        ADC_Tick();
        GATEIO_Tick();
        DCMOTOR_Tick();
    }

    /* ... 其余调度保持不变 ... */
}
```

### 3.2 eeprom_drv.c

头部增加 `#include "wdg.h"`，并把当前重复的 `delay_ms(10);delay_ms(10);` 改为单次等待 + 喂狗：

```c
IIC_Stop();                  /* 产生一个停止条件 */
delay_ms(10);                /* AT24C02 最大写周期 5ms，10ms 已是 2 倍余量 */
WDG_Feed();                  /* 单字节 10ms；32B 槽 320ms、四槽连续 1.28s，必须在此喂狗 */
```

> 这里**必须删掉重复的第二个 `delay_ms(10)`**：20ms/字节时，四个 32B 凭据槽连续写就是 2.56s，即使每字节喂狗，主循环也会被整体拖慢 2.56s，导致 GPRS 心跳与串口搬运长期停摆；去掉后总耗时降到 1.28s，同时看门狗窗口留出足够余量。

### 3.3 lcd12864.c

```c
/* ST7920 needs about 1.5 s after power-on before accepting commands.
   delay_ms() saturates at ~1864 ms @72 MHz, so wait in three 500 ms
   slices; feed the watchdog after each slice. */
delay_ms(500);
WDG_Feed();
delay_ms(500);
WDG_Feed();
delay_ms(500);
WDG_Feed();
```

同时把原注释里"qibiji_zxl has no watchdog"的说明删掉，避免后续维护者误以为喂狗可以省略。文件头部加 `#include "wdg.h"`。

### 3.4 gprs_4g.c

`GPRS_4G_Init()` 的复位脉冲：

```c
GPRS_RST_ON();
delay_ms(500);
GPRS_RST_OFF();
WDG_Feed();                  /* 上电复位脉冲 500ms */
```

`GPRS_4G_Reset()` 的长复位（由 `net_liveness.c` / `gprs_at.c` 在主循环中调用）：

```c
s_last_reset_ms = g_sys_ms;
s_reset_ever = 1u;
GPRS_RST_ON();
delay_ms(1000);
GPRS_RST_OFF();
WDG_Feed();                  /* 运行期复位 1s */
GPRS_4G_Init();              /* 内部 500ms 脉冲后已喂狗 */
```

文件头部加 `#include "wdg.h"`。

### 3.5 禁止喂狗的位置

| 位置 | 原因 |
|---|---|
| `TIM3_IRQHandler` / `TIM3_10ms_Init` 的中断回调 | 中断若还在跑、主循环已经死锁，在 ISR 里喂狗会让故障永久隐藏 |
| `EXTI9_5_IRQHandler`（LINKA） | 同上 |
| `GPRS_AT_RxPump` 等每轮调用的短函数 | 主循环头已经覆盖，重复喂狗没有收益 |
| `delay_ms()` / `delay_us()` 内部 | 会让所有长延时自动免疫看门狗，等于没开 |

全局只允许出现两个喂狗函数名：`WDG_Feed()`（业务侧）与 `IWDG_ReloadCounter()`（仅 `wdg.c` 内部）。完成后用全局搜索确认 `WDG_Feed` 只出现在 `main.c`、`eeprom_drv.c`、`lcd12864.c`、`gprs_4g.c` 四类文件里。

## §4 main 初始化顺序（与 EEPROM 的衔接）

```c
NVIC_Configuration();
DEBUG_UART_Init();
WDG_Init();                       /* 看门狗必须先启动，才能覆盖后续长阻塞初始化 */
WDG_Feed();
if (g_wdg_reset_cause != 0u)
    DEBUG_UART_SendString("reset cause: IWDG\r\n");

KEY_Init();
delay_init();
LCD12864_Init();                  /* 1.5s，三段各喂一次 */
LCD_BACKLIGHT_Init();
LCD_PAGES_Init();
ADC1_Init();
GATEIO_Init();
DCMOTOR_Init();

AT24CXX_Init();                   /* I²C 初始化 */
AT24CXX_Check();                  /* 自检 + 闸门参数播种（每字节写都喂狗） */
dcmotor_param_load();
gprs_config_load();
DCMOTOR_SetMaxTurns(g_gate_maxturns);
ADC_SetStallThresholdMa(g_motor_warning_curr_upper);

GPRS_PORT_Init(115200);
GPRS_RTC_Init();                  /* DS1302 位操作，毫秒级 */
GPRS_4G_Init();                   /* 500ms 复位脉冲，脉冲后喂狗 */
UartTx_Queue_Init();
UartRx_Queue_Init();
TIM3_10ms_Init();
```

关键点：

1. **`WDG_Init()` 必须在 `LCD12864_Init()` 和 `AT24CXX_Check()` 之前**，否则这两段最长的初始化不受监控；同理，喂狗点必须先于阻塞点存在；
2. **`WDG_Init()` 之后不要再插入任何超过 1.5s 且未喂狗的新初始化**，新增外设时按 §2 的预算表评估；
3. `AT24CXX_Check()` 的播种最多写 6 字节（60ms），远小于窗口，无需额外处理；
4. 看门狗复位不会清 RAM，`g_gate_maxheight` 等参数保持复位前的值；但不要依赖这一点做业务逻辑，上电仍按 EEPROM 重新加载。

## §5 与《EEPROM重构操作建议》的同步改动

看门狗接入后，EEPROM 文档里"本阶段不启用看门狗"的表述已按下表完成同步（共三处）：

| 文档位置 | 原内容 | 改为 |
|---|---|---|
| §1 `eeprom_drv.c` 改动说明 ① | "去掉 `IWDG_Feed()`（本阶段不启用看门狗）" | "保留 `IWDG_Feed()`（改名为 `WDG_Feed()`），见《看门狗重构操作建议》§3.2" |
| `eeprom_drv.c` 源码 `AT24CXX_WriteOneByte` | 只有 `delay_ms(10)` | `delay_ms(10); WDG_Feed();`，并补 `#include "wdg.h"` |
| §6 "原工程的 `24cxx.c` 里这些**保留**" 条目 | "`delay_ms(10)`（EEPROM 写周期等待，本阶段不启用看门狗）" | "`delay_ms(10)` + `WDG_Feed()`（写周期等待并喂狗）" |

另外，zxl 工程当前 `eeprom_drv.c` 的实际代码是 `delay_ms(10);delay_ms(10);`，与本建议不一致，按 §3.2 收敛为单次 10ms 后再接喂狗。

其他已按本文同步的文档：

- 《LCD重构操作建议_驱动层》§4.3、§8：`LCD12864_Init()` 恢复三段等待后喂狗，依赖清单加入 `wdg.h`；
- 《GPRS重构操作建议》：`gprs_4g.c` 加入 `wdg.h`，`GPRS_4G_Init()` / `GPRS_4G_Reset()` 的复位脉冲后各喂一次；
- 《GPRS重构操作建议_阶段二起》§7.2、§14.3：更新 `WDG_Feed()` 的落地位置说明，明确 MCU 软复位前无需再喂。

## §6 调试注意

1. **不要为了"调试时总被复位"去改大窗口**。STM32F1 的 `DBGMCU_CR` 只能由调试器写入，固件调用 `DBGMCU_Config()` 无效；调试时在 Keil → Options for Target → Debug → Settings 勾选 **Stop Watchdog Counters**（ST-Link/ULINK 驱动会写该位）。串口 ISP 下载、不接调试器时该选项不生效。
2. **IWDG 一旦使能无法软件关闭**，只能复位。需要"无狗版本"时，只能在 `WDG_Init()` 里用编译宏整体跳过，不能事后关。
3. **看门狗不是通信异常处理手段**：GPRS 掉线仍走原有状态机重连（`net_liveness.c` / `gprs_at.c`），不能靠复位解决业务级超时。
4. **复位来源判读**：`g_wdg_reset_cause == 1` 只说明**本次上电前**发生过 IWDG 复位，不代表本次运行一定有问题；若反复出现，结合串口 banner 打印次数与 `g_sys_ms` 判断复位周期。
5. **复位后电机状态**：IWDG 复位会重新执行 `DCMOTOR_Init()`，继电器输出回到关闭态；若现场出现复位后闸门继续动作，说明继电器驱动存在硬件自保持，与固件无关。

## §7 验证清单

1. **编译接入**：`HARDWARE/WDG/wdg.c` 加入 Keil 工程并 Rebuild，链接无 `IWDG_WriteAccessCmd` / `IWDG_SetPrescaler` 等未定义告警；`wdg.c` 中不得出现 `DBGMCU_Config`（工程未编译 `stm32f10x_dbgmcu.c`）。
2. **冷启动**：连续冷启动 10 次，串口每次完整打印初始化日志，中途无重启；`reset cause: IWDG` 不出现。
3. **LCD 窗口**：冷启动 1.5s 等待期间不复位（若复位，检查三段之间是否漏了 `WDG_Feed()`）。
4. **EEPROM 长写**：用 `gprs_store_write_str()` 连续写四个 32B 槽，全程不复位；串口无发送队列卡死（长写期间每 8 字节的 `UartRx_PumpFromDma(0)` 仍生效）。
5. **GPRS 复位**：断网触发 `GPRS_4G_Reset()`（1s 脉冲）或平台触发复位，复位期间不复位，复位后模块 banner 正常、能重新上线。
6. **人为挂死**：在 `APP_DispatchKey()` 里临时插入 `while(1)`，确认 2.1~3.2s 内芯片复位，重启后串口出现 `reset cause: IWDG`；验证后删除。
7. **中断不喂狗**：全局搜索 `WDG_Feed`，确认命中范围与 §3 清单一致，`TIM3` / `EXTI9_5` 中断中无调用。
8. **断点调试**：在 `DCMOTOR_Process()` 处设置断点并停留 5s，确认不复位（Keil 调试设置已勾选 Stop Watchdog Counters）；断开调试器全速运行 10 分钟不复位。
9. **复位安全**：人为触发 IWDG 复位，确认继电器在复位瞬间断开、电机停转，重新上电后闸门不会自行动作。
