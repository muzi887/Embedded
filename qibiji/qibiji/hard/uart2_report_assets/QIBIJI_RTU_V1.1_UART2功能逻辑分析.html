结论摘要

当前工程中的 UART2 是 STM32F103 与 WH‑LTE‑7S1 4G 模块之间的专用通信口，不是调试口，也不承担 RS‑485。它同时包含五种逻辑：

  1. 物理串口与 DMA 接收：PA2/PA3、115200 8N1、DMA1_Channel6、IDLE 中断。
  2. AT 命令通道：用于查询 ICCID、MQTTCID、CSQ，以及近场重新配置模块。
  3. MQTT 主题化串口协议：上行以“主题槽位号 + 逗号 + JSON”发送；下行由模块回送 AT 文本或 JSON。
  4. 业务协议处理：属性上报、事件上报、服务回执、配置下发、属性读取、对时。
  5. 连接自愈：LINKA 去抖、AT 初始化状态机、应用心跳、对时超时和 4G 模块硬复位。

四个“在线”概念必须分开看：

状态含义
GPRS_LINKA / gprsonlineflag模块蜂窝链路原始状态
atflag_online收到过模块启动 banner
gprs_is_ready()MCU 状态机进入 NORMAL
NetLiveness_IsServerConfirmed()最近 240 秒内收到过平台心跳回执

“模块已联网”不等于“MQTT 已连接并订阅成功”，更不等于“平台已经确认在线”。

3. UART2 接收链

3.1 DMA 接收

DMA 使用 Normal 模式，每次最多接收 1024 字节。IDLE 中断到来后：

Usart2_Rec_Cnt =
    DMA_Rec2_Len - DMA_GetCurrDataCounter(DMA1_Channel6);

然后重新装载 DMA 计数器。若模块在 1024 字节内仍持续发送、没有形成 IDLE 间隔，DMA 可能自然结束而代码没有 DMA 传输完成中断来继续搬运，这是当前接收链的硬边界。

3.2 IDLE 中断与双槽暂存

接收暂存：

rxStage[0][1024]
rxStage[1][1024]

IDLE 中断在普通模式下把当前 DMA 帧复制到写指针指向的槽：

  1. 当前槽为空：直接写入；
  2. 两槽都满：清除当前写指针所指的最旧槽；
  3. g_uart2_rx_overwrite++；
  4. 写入新帧并切换写指针。

这样主循环即使被长 EEPROM 写阻塞，也不会由下一次 DMA 立即覆盖上一帧。最多保存最近两帧。

中断还会在帧内搜索 ASCII 字符串 WH-LTE-7S1，命中则设置 g_uart2_banner_seen=1。

3.3 普通模式与 AT 配置模式

当 uart3_at_sequence_should_run()!=0 时：

  • IDLE 中断不再复制到乒乓槽；
  • 普通主循环不运行；
  • AT 配置状态机直接检查 DMA_Rece_Buf2 和 DMA 剩余计数；
  • AT 序列完成或失败后，重新把 UART2 交回普通接收链。

3.4 主循环取帧

UartRx_PumpFromDma(verbose)：

  • 一次最多取 4 个暂存帧；
  • 取槽和复制进环形缓冲时短暂关闭中断；
  • verbose=1 时打印 [GPRS] RX[len]: 原文；
  • EEPROM 长写内部调用 verbose=0，只搬运不打印；
  • 接收数据进入 3072 字节线性环形缓冲；
  • 再按最多 1023 字节切块，进入 8 项接收帧队列。

接收系数的完整层次：

层容量
单次 DMA1024 B
乒乓暂存2 × 1024 B
环形缓冲3072 B
接收帧队列8 × 1024 B

3.5 丢包统计

计数含义
g_uart2_rx_overwrite两槽都满，旧帧被覆盖的次数
g_uartRx_dropped_bytes环形缓冲满，尾部数据被截断的字节数

二者发生变化时，Gprs_Process() 会打印：

4. 接收解析

Parse_Process() 循环取出接收帧：

帧中有完整 JSON？
  ├─ 是：先识别空对象 {}，否则严格信封校验并按 type 分发
  └─ 否：交给 UartTx_OnRecv(frame, len, 1)，作为 AT 回执

JSON 提取使用大括号深度匹配。它不识别字符串内部的 {、}，如果 JSON 的字符串值包含花括号，可能误切帧。

4.1 严格信封

普通下行 JSON 必须包含：

id           非空字符串
productKey   非空字符串
deviceKey    非空字符串
type         非空字符串
body         JSON 对象

允许的 type：

service
config
property
property_get
request_reply

当前没有把信封中的 productKey/deviceKey 与 EEPROM 本地值逐字比较，只检查其非空。

4.2 AT 回执

无 JSON 的帧交给 UartTx_OnRecv()：

  • 仅检查当前发送队首；
  • AT 项必须同时匹配 resp_key 和其后的 OK；
  • 匹配成功：执行回调并出队；
  • 不匹配：继续等待，超时后重发。

注意：UartTx_OnRecv() 在“队首存在但类型不匹配”的路径没有任何显式 return，而函数返回类型为 u8，属于代码正确性问题。

5. 发送链与队列

5.1 物理发送

Usart2_Send() 不使用 DMA：

while (USART_GetFlagStatus(USART2, USART_FLAG_TC) == RESET);
USART_SendData(USART2, buf[t]);

115200 8N1 下单字节约为：

$$ t_{\mathrm{byte}}=\frac{10}{115200}\approx86.8\ \mu s $$

1 KiB 约需 89 ms。发送期间主循环阻塞。

5.2 统一发送队列

参数值
队列深度8
AT 命令长度最大 31 B
AT 响应关键词最大 15 B
AT 超时1000 ms
AT 最大重发2
JSON 长度最大 1023 B
JSON 回调键最大 19 B
无回调 JSON 间隔300 ms

规则：

  • UartTx_Push_JSON() 要求 gprs_is_ready()==1；
  • UartTx_Push_AT() 在离线状态也可入队；
  • 队列满时返回 0；上报不会持久化，直接丢失；
  • 同一时刻只允许一个队首处于发送/等待状态；
  • AT 超时最多重发两次；
  • 未识别的迟到回执不会匹配后续指令。

5.3 JSON 等待的实际行为

当前所有 UartTx_Push_JSON() 调用者都传入 callback=NULL：

  • 实际等待时间固定为 300 ms；
  • UART_TX_JSON_TIMEOUT_MS=5000 与 max_retry=2 不会触发；
  • JSON 的 UART2 回调匹配分支当前没有业务调用者；
  • 平台 ACK 是通过新的下行 JSON 独立识别的；
  • “发送队列已空”只表示 UART2 已发出，不代表平台已收到或接受。

6. GPRS 链路状态机

6.1 OFFLINE

条件：

  • link_state==1；
  • 且 atflag_online 为真或曾检测到掉线恢复；

满足后进入 AT_INIT_PUSH。

若离线持续至少 60 秒，且距上次模块硬复位至少 5 分钟，则调用 GM4G_Reset()。

6.2 AT_INIT_PUSH / WAIT

一次性入队三条 AT：

usr.cn#AT+ICCID?
usr.cn#AT+MQTTCID?
usr.cn#AT+CSQ?

成功标志：

  • ATflag_ICCID；
  • ATflag_MQTTCID；
  • ATflag_CSQ。

三条全部置位后进入 NORMAL。

6.3 失败与退避

  • 单条 AT：1 秒超时，最多重发 2 次；
  • 三条处理后仍不齐全：等 10 秒；
  • 最多约 3 轮初始化；
  • 第 3 轮仍失败：进入 30 分钟 BACKOFF；
  • 30 分钟后重新进入 AT_INIT_PUSH。

gprs_state_machine() 先处理接收，随后才由状态机消费本轮 AT 回调，因此同一主循环内通常可以立即看到成功标志。

6.4 NORMAL

  • gprs_is_ready()==1；
  • 允许业务 JSON 入队；
  • 每 10 分钟发一次 AT+CSQ?；
  • 链路由高变低并持续 2 秒时，清空发送队列、取消对时并回 OFFLINE；
  • 链路恢复需要高电平持续 500 ms。

6.5 回调内容限制

  • CSQ 回调只复制前两位数字；
  • ICCID 回调按固定位置抽取数字；
  • MQTTCID 回调复制可打印 ASCII；
  • 只要响应中存在对应前缀并匹配了 OK，即使内容格式异常，标志也可能置位。

因此 AT 初始化成功主要表示“模块对命令有应答”，不代表卡片/号码内容一定合法完整。

7. 主循环顺序

正常主循环中，UART2 接收早于业务处理：

PropertyReport_Process()
    ↓
Gprs_Process()
    ├─ 收帧
    ├─ 解析下行
    ├─ 推进链路状态
    ├─ 调度对时
    ├─ 处理心跳
    ├─ 发送队首
    ├─ 对时重试
    └─ 延时复位

好处：

  • 收到平台服务命令后可在同一轮生成回执并入发送队列；
  • 对时回执先更新 DS1302，再允许心跳模块发送；
  • ReSet 回执在被解析后不会被立即打断，而是在后续轮次执行真正复位。

代价：

  • 单条 JSON 最长约 89 ms 的阻塞发送；
  • 解析、cJSON 和日志都会占用主循环时间；
  • 输入队列拥塞时，状态机和业务处理可能延迟。

8. 下行业务功能

8.1 type=service

serviceCode行为
setValue设置目标开度，并按目标与当前开度启动升降
stopGate立即请求停止电机，返回成功回执
getFirmware返回 FirmwareVer
ReSet入队成功回执，等待至少 1 秒并清空队列后复位 MCU
setUpdateValue写入 OTA 更新标志
getConfig返回电流上限、OTA 开关、阀高配置

未识别的 serviceCode 当前没有默认失败回执。

8.2 type=config

支持的 configCode：

MotorMaxCurrConfig
GateMaxHeightConfig
OTAEnableFlagConfig

处理流程：

  1. 校验 configCode；
  2. params 必须只有一个子项；
  3. 校验参数名和类型；
  4. 写 EEPROM；
  5. 回读验证；
  6. 通过 up/service/reply 返回 config.push。

8.3 type=property_get

  1. 生成当前全量属性快照；
  2. 通过 up/service/reply 带回原 id；
  3. 再发 up/property/post，把属性写入平台点位。

8.4 type=request_reply

用于 sys.timeSync：

  • 只接受当前在途请求的 id；
  • code 必须为 0；
  • 读取 body.output.serverTime；
  • UTC 加 8 小时；
  • 写 DS1302；
  • 调用 NetLiveness_OnTimeSyncOk() 解锁首帧心跳。

8.5 空对象 {}

这是平台对极简心跳的回执：

  • 只有存在待确认心跳时才处理；
  • 清除 pending；
  • 连续 miss 清零；
  • 记录最近 ACK 时间；
  • 作为“双向通道可用”的证据。

该功能由 BLE 参数写入触发，但实际配置对象是 UART2 上的 4G 模块。文件名 uart3_at_sequence.c 是历史命名，不代表它使用 USART3。

10.2 超时与失败

每一步：

  • 发送前重新装载 DMA；
  • 最长等待 2000 ms；
  • 成功帧间隔 50 ms；
  • 40 ms 串口静默可作为无 IDLE 时的兜底帧结束条件。

失败策略：

  • AT+CACHEN=OFF 失败时只告警并跳过；
  • 其他步骤失败直接终止；
  • 不重试整条序列；
  • 成功完成才保存 productKey/deviceKey；
  • 随后 GM4G_Reset()，再执行 NVIC_SystemReset()。

10.3 主循环影响

序列 busy 时，main 循环每轮只执行：

  • 喂看门狗；
  • BLE poll；
  • UART2 AT 状态机。

按键、ADC、电机控制、LCD、属性上报、普通 GPRS 和 RS‑485 都暂停。若电机在配置前正在运行，继电器不会因为该配置流程自动停止。

11. 对时与心跳

11.1 对时

进入 NORMAL 后：

  1. 先热身 2 秒，等待模块建立 MQTT 会话和订阅；
  2. 发 sys.timeSync 请求；
  3. 稳态每次等待 15 / 30 / 60 秒；
  4. 等待首帧心跳期间，所有等待压缩为 5 秒；
  5. 每次使用新的毫秒时间戳 id；
  6. 收到匹配回执后写 DS1302；
  7. 正常稳态每 24 小时发起一轮。

掉线恢复后，如果此前没有收到过合法下行，先不下发正式对时，而是在 60 秒节奏下发送单帧探测，直到任一合法下行证明双向通道可用。

11.2 心跳

首帧心跳必须等校时成功。之后：

  • 每 120 秒发送 2,{}；
  • 平台回 {}；
  • 最近回执在 240 秒内，显示“平台已确认”；
  • 连续 3 次无回执，才考虑模块硬复位；
  • 自愈复位最小间隔为 15 分钟；
  • 掉线或模块复位时，保留 miss 计数，避免复位风暴。

12. 状态诊断模型

排障时应逐层确认：

  1. 蜂窝链路：LINKA 是否稳定高、CSQ 是否正常；
  2. 模块可交互：是否收到 banner，三条 AT 是否成功；
  3. 应用通道：是否拿到 sys.timeSync 回执和心跳 {} 回执；
  4. 业务协议：Topic 槽位、JSON 信封和平台接受状态是否正确。

常见误判：

  • LINKA 高就认为平台在线；
  • AT 查询成功就认为 MQTT 订阅成功；
  • 发送队列为空就认为平台已收到；
  • 平台在线就认为属性/事件一定被接收。

13. 模块复位

GM4G_Reset()：

  1. PA1 拉高，使 Q3 拉低模块 RESET，持续约 1000 ms；
  2. PA1 拉低；
  3. 调用 GM4G_Init()；
  4. GM4G_Init() 再拉高 500 ms，然后拉低。

因此实际阻塞约 1.5 秒，源码注释中的“约 1 秒”偏短。

触发入口：

路径条件
链路离线离线≥60 秒且复位间隔≥5 分钟
心跳失联miss≥3 且复位间隔≥15 分钟
对时失败等待首帧心跳期间连续失败
BLE 重配置23 条 AT 成功后

14. 静态代码审查发现

P0：可能造成数据错误或异常行为

  1. DMA 为 Normal 模式且没有 DMA 传输完成中断。超过 1024 字节且没有 IDLE 间隔的帧可能停止接收。
  2. 没有启用 UART 溢出、噪声、帧错误中断。
  3. UartTx_OnRecv() 在“队首类型与 strtype 不匹配”时缺少返回语句。
  4. Gprs_ClockSync_IssueAttempt() 不检查 UartTx_Push_JSON() 的返回值；队列满时仍进入等待，可能在没有真正发送的情况下超时。
  5. AT 配置序列期间直接读取 DMA，若模块异步送来 JSON/其他 AT 文本，可能被误当成当前命令应答。

P1：协议和可靠性

  1. 当前业务 JSON 全部使用 callback=NULL，5 秒超时和 2 次 JSON 重试不会发生。
  2. JSON 每个仅占 300 ms 队列，发送队列为空 不代表平台收到。
  3. AT 只有“关键词 + OK”出现在同一帧时才匹配；跨帧响应会超时。
  4. UartRx_Extract() 按 1023 字节切块，帧队列项不一定等于一个完整协议帧。
  5. 严格信封只校验 productKey/deviceKey 非空，没有与本地值比较。
  6. AT 回调只要找到前缀就置成功标志；CSQ、ICCID 或 MQTTCID 内容格式异常时可能仍被接受。

P2：可维护性和诊断

  1. usart.h 中 USART2 DMA 通道注释写反。
  2. uart3_at_sequence.c 实际操作 UART2，文件名误导。
  3. Usart2_Rec_Cnt、UART2_RX_Complete 在中断和主循环间共享，但没有 volatile。
  4. UartRx_PumpFromDma() 的日志打印使用暂存槽指针，打印期间槽可能被中断改写；功能数据已先复制，主要影响日志可信度。
  5. Gprs_PeriodicPush_Process() 当前主要处理对时，不是周期属性推送；gprs_periodic_last_tick 和 GPRS_PERIODIC_PUSH_INTERVAL_MS 基本未使用。
  6. AT 命令长度采用硬编码，如 ICCID 命令长度 18；修改命令文本后容易失配。
  7. handleAT_CCLK() 与 ATflag_CCLK 是遗留路径，当前对时主要走 JSON sys.timeSync。
  8. UartRx_GetRemainingBuffer() / UartRx_Consume() 在工程中没有实际调用者。
  9. EventPostSimple() 仍使用主题槽位 1，但它当前没有活动调用；如果以后启用，需确认是否应改为事件槽位 4。

15. 端到端时序

15.1 上电

uart2_init
  → GM4G_Init 500 ms 复位脉冲
  → 模块输出 WH-LTE-7S1 banner
  → UART2 IDLE 收帧
  → banner_seen / atflag_online
  → LINKA 稳定高 500 ms
  → AT_INIT_PUSH
  → ICCID / MQTTCID / CSQ 全部 OK
  → NORMAL
  → 2 s 热身
  → sys.timeSync
  → DS1302 写时间
  → 首帧心跳 2,{}
  → 平台回 {}
  → 平台确认在线

15.2 收到平台服务

MQTT down/service/invoke
  → UART2 收到 JSON
  → Parse_Process
  → 信封校验
  → service 分支
  → 执行业务
  → 主题槽位 6 回执入队
  → UartTx_Queue_Process
  → Usart2_Send

15.3 链路掉线

LINKA 低
  → 2 s 去抖
  → OFFLINE
  → 清发送队列
  → 取消在途对时
  → 62 s 后允许 GM4G_Reset（若距上次复位 ≥5 min）
  → 模块重启
  → 重新检测 banner / LINKA / AT

15.4 近场重新配置

BLE 写入 MQTT 参数
  → uart3_at_sequence_request_set(1)
  → main 跳过普通任务
  → 构建 23 条 AT
  → 逐条 2 s 等待
  → 全部成功
  → 保存 PK/DK
  → GM4G_Reset
  → NVIC_SystemReset

17. 最终判断

UART2 的当前实现已经形成较完整的通信框架：

  • 中断/DMA/双槽/环形缓冲保证主循环长阻塞时仍能接收；
  • AT 与 JSON 共用发送队列，避免物理串口并发写；
  • 采用状态机而非固定延时完成模块初始化；
  • 使用主题槽位把 MQTT 发布和订阅映射到简明串口格式；
  • 通过对时、应用心跳和模块复位构成多层恢复。

主要短板集中在边界条件和协议确认：

  • DMA 不是循环模式，缺少 DMA 完成中断；
  • 未启用 UART 错误中断；
  • JSON 业务发送没有串口确认和有效重试；
  • AT 解析依赖同一帧内的关键词和 OK；
  • 队列满、对时入队失败、状态变量可见性和未返回路径需要加固；
  • 线上线下状态必须在 UI、日志和平台诊断中分层表达。
