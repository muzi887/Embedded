## Gprs_Process() 代码解读文档

- 用户要求生成文件说明 `Gprs_Process()` 的逻辑（延续 ADC / Dcmotor / Lcd 三份文档的体例）。
- 产出：`docs/Gprs_Process_explained.md`（8 节 + 参数速查表，带源码行号对照，含 Mermaid 数据流图）。未改动任何 `.c`/`.h` 源码。
- 覆盖：主循环上下文（`uart3_at_sequence_main_loop_tick()` 会整体跳过 GPRS）、七步流水线的分步耗时段、`gprs_rx_datas()` 三层搬运（乒乓槽→环形缓冲→帧队列）与 banner→`atflag_online` 映射、`Parse_Process()` 的判定顺序（空对象心跳回执必须先于严格信封校验；信封暂存先于通道证据）、五类 type 与 8 个 serviceCode 分支、状态机六态与 `gprs_is_ready()` 总闸、`Gprs_PeriodicPush_Process()`（名不副实，实为对时：2s 热身 / 等通道 / 15-30-60s 退避 / 24h）、`NetLiveness_Process()`（120s 心跳、3 次判失联、15min 复位节流、首帧必须等 timeSync ok、等待期 5s 快节奏 + 3 次对时失败硬复位）、`UartTx_Queue_Process()`（一发一收，AT 1000ms×2，JSON 有回调 5000ms、无回调仅 300ms）、`Gprs_ClockSync_Process()`、`Gprs_Reset_Process()`（回执出队+1s 才复位）、丢包计数可观测。
- 核心结论：① 这是"收→解→连→报→活→发→复位"的七步非阻塞流水线，跨轮状态全在各模块 static 里；② 上下行是两个独立队列，`Parse_Process` 是唯一纽带，同一轮内即可完成"命令→执行→回执发出"；③ 不在 NORMAL 时上行全部静默丢弃（不缓存、不重发），掉线期间事件在云端永久缺失；④ `ReSet` 采用"先回执、后复位"两段式，因为发送状态机在解析之后才跑。
- 记录但未修改的问题（按严重度）：
  - F1（高）`Gprs_ClockSync_OnReply` 先清 pending 再调 `reply_cjson_clock`，后者在 `body.code != 0` 时直接 return：既不解锁心跳、也不计 `s_ts_fail`、也不重试 → 首帧心跳被压住最长 24h（等下一轮对时周期）。
  - F2（高）同一轮内：第 2 步执行命令并入队回执 → 第 3 步确认掉线 `UartTx_Queue_Init()` 清空队列 → 设备已动作但回执永久丢失，平台记执行超时。
  - F3（中）属性无周期兜底：`Gprs_PeriodicPush_Process` 实为对时，`GPRS_PERIODIC_PUSH_INTERVAL_MS` 与 `gprs_periodic_last_tick` 是死代码；属性只在开度变化 ≥2% 或停机强制时上报。
  - F4~F10（中/低）：非 NORMAL 静默丢包无告警；`SettingValue` 无条件回 success 且 `(u8)value` 无范围校验；校验失败 `return` 而非 `continue`；`property_get` 复用 `g_json_msg_service` 未 memset 导致 commandNo 残留；`UartTx_Push_JSON` 返回值被上层忽略；`NetLiveness_IsAck` 只认空对象；`UartTx_OnRecv` 缺 return。
