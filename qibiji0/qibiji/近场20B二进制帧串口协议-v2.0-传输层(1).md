## 1. 分层定位

### 1.1 本文范围

**本文规定**：线帧格式、通道方向、FLAGS 分片、逐对交互、opaque 重组与 CRC。应用载荷语义见 [应用层专版](./近场20B二进制帧串口协议-v2.0-应用层.md)。

```text
┌─────────────────────────────────────────────────────────┐
│  应用层（见专版）                                         │
│  JSON / TLV / 寄存器表 / 业务错误码 / 读·写语义            │
│  → 见 [近场20B二进制帧串口协议-v2.0-应用层.md](./近场20B二进制帧串口协议-v2.0-应用层.md) │
├─────────────────────────────────────────────────────────┤
│  SBF-20 传输层（本文）                                    │
│  线帧格式、帧方向、FLAGS 分片、逐对交互、超时、CRC         │
│  交付两条 opaque 字节流：请求侧 + 响应侧                   │
├─────────────────────────────────────────────────────────┤
│  物理链路                                                 │
│  UART 9600 8N1（MCU↔模组）+ BLE GATT（App↔模组）         │
│  → 见 [SBF-20物理链路说明.md](./SBF-20物理链路说明.md)     │
└─────────────────────────────────────────────────────────┘
```

**传输层职责**：按逐对请求/响应与 FLAGS 重组，分别得到 **请求 opaque** 与 **响应 opaque** 两条字节流，交给应用层解析。

### 1.2 物理链路参数

`App` ↔ **BLE GATT** ↔ `DX-BT24` ↔ **UART** ↔ `MCU`（点对点）。本节只约定 **链路与 GATT 参数**；**帧在链路上的走向**由 §1.3 发起方/应答方角色决定（表 1、表 2）。接线与逐字节旅程见 [SBF-20物理链路说明.md](./SBF-20物理链路说明.md)。

| 项 | 约定 |
| --- | --- |
| UART | **9600**，8N1 |
| 接线 | 对端 **TX** → 模组 **RXD**；对端 **RX** ← 模组 **TXD**（交叉） |
| Service | `0000ffe0-0000-1000-8000-00805f9b34fb`（`FFE0`） |
| GATT 写 | **`FFE2`** Write（可 Write Without Response） |
| GATT 收 | **`FFE1`** Notify（须写 CCCD 订阅） |
| 连接模型 | 同一 BLE 连接 **串行**：同一时刻仅一个未完成的 **请求↔响应会话** |
| 单包上限 | 线帧 **≤ 19 B**；兼容 ATT 默认 **20 B** 载荷 |

### 1.3 发起方与应答方

本协议传输层为 **请求-应答** 模型。**发起方 / 应答方是会话角色**，与 App、MCU 身份 **无永久绑定**——**App 或 MCU 均可担任发起方或应答方**。物理参数见 §1.2；**近场配置常态**下的通道映射见 **表 1**。

```text
┌─────────────┐   请求帧    ┌─────────────┐
│  发起方      │ ─────────► │  应答方      │
│             │ ◄───────── │             │
└─────────────┘   响应帧    └─────────────┘
```

| 角色 | 传输层行为 |
| --- | --- |
| **发起方** | 发出 **请求帧**；收取 **响应帧**；维护 **请求 opaque** |
| **应答方** | 收取 **请求帧**；发出 **响应帧**；维护 **响应 opaque** |

**谁担任发起方**：由 **谁在物理链路上发出本会话第一片请求帧** 决定。

**请求帧 / 响应帧** 由 **会话角色** 定义，**不是** 永久绑定某一 GATT UUID 或 UART 方向（§5）。

#### 表 1：App 担任传输层发起方（近场配置常态）

| 线帧 | App | MCU |
| --- | --- | --- |
| **请求帧** | Write **`FFE2`** | **UART RX** 收 |
| **响应帧** | Notify **`FFE1`** 收 | **UART TX** 发 |

#### 表 2：MCU 担任传输层发起方

| 线帧 | MCU | App |
| --- | --- | --- |
| **请求帧** | **UART TX** 发 | Notify **`FFE1`** 收 |
| **响应帧** | **UART RX** 收 | Write **`FFE2`** 发 |

**与应用层的关系**（重要）：

- **传输层**：App / MCU **均可** 担任发起方（上表 1 或表 2）。
- **应用层**（JSON 读/写/探活业务）：**仅 App 担任发起方**，MCU **仅** 担任应答方。见 [应用层专版 §1.3](./近场20B二进制帧串口协议-v2.0-应用层.md)。
- 近场配置产品：**传输层 + 应用层** 均走 **表 1**；MCU 固件 **至少** 实现表 1 下应答方逻辑；表 2 供主动上报等扩展场景。

**记忆口诀**：**传输看角色，应用定 App 发起；表 1 是配置常态。**

> UART 上可能出现 BT24 密码等 **非 `0x55` 杂字节**；须以 `SOF=0x55` 同步（§10.1）。

## 2. 传输层能力一览

以下按 **发起方 / 应答方** 会话角色描述。

### 2.1 发起方能力

| 能力 | 传输层行为 |
| --- | --- |
| **探活** | 空 opaque 一对（`FLAGS=0x00`）；发请求帧、收响应帧 |
| **业务会话** | 按 FLAGS 分片发送请求 opaque；逐对等待响应帧 |
| **接收响应 opaque** | 按 `INDEX` 拼接响应帧 `PAYLOAD` |
| **节奏控制** | 收响应帧(`INDEX=i`) 后，若还有下一片请求帧，**≤ 50 ms** 内发出(`INDEX=i+1`) |
| **超时判定** | 发请求帧(`INDEX=i`) 后 **500 ms** 内须收到同 `INDEX` 响应帧 |
| **串行约束** | 当前会话末对收齐后，方可发起下一会话 |

### 2.2 应答方能力

| 能力 | 传输层行为 |
| --- | --- |
| **响应探活** | 收请求帧 → 回 `FLAGS=0x00` 响应帧（如 `55 02 00 df`） |
| **响应业务** | 每片请求帧 **500 ms** 内回一片响应帧（同 `INDEX`） |
| **接收请求 opaque** | 按 `INDEX` 拼接请求帧 `PAYLOAD` |
| **发送响应 opaque** | 响应分片发出；中间片 `PAYLOAD` 可为空 |
| **INDEX 成对** | 响应帧 `INDEX` 与请求帧相同 |
| **应答节奏** | 发起方可能 **≤50 ms** 后发下一请求；本片须在 **500 ms** 内响应 |

### 2.3 双方共同遵守的传输契约


| 契约             | 说明                                        |
| -------------- | ----------------------------------------- |
| **逐对交互**       | 1 片请求帧 : 1 片响应帧，`INDEX` 相同；须逐对发送          |
| **双 opaque 流** | 一次会话产出 **请求 opaque** 与 **响应 opaque**，彼此独立 |
| **FLAGS 独立**   | 请求侧与响应侧的 `FLAGS.MORE` 各自表示本方向是否还有后续片      |
| **会话结束**       | **末对** 请求帧与响应帧的 `FLAGS.MORE` **均为 0**（中间对可任一侧 `MORE=1`） |
| **超时**         | 对超时则会话失败；由应用层重新发起完整会话                     |
| **长度**         | opaque 总长度 `N` 由应用层验长与解析                  |

## 3. 术语


| 术语              | 含义                                                  |
| --------------- | --------------------------------------------------- |
| **发起方**         | 发出请求帧、收取响应帧（会话角色，见 §1.3）                     |
| **应答方**         | 收取请求帧、发出响应帧（会话角色，见 §1.3）                     |
| **帧（Frame）**    | 线上一个完整 SBF-20 单元：`SOF` … `CRC8`                     |
| **FLAGS**       | 线帧 `DATA` 首字节，分片控制（请求/响应帧均必有）                       |
| **PAYLOAD**     | `DATA` 中 `FLAGS` 之后的 opaque 字节（0～15 B）              |
| **一对（Pair）**    | 一片 **请求帧** + 一片 **响应帧**，`INDEX` 相同                  |
| **会话（Session）** | 从 `INDEX=0` 起至 **末对**（双方 `FLAGS.MORE` 均为 0）的全部 Pair |
| **请求 opaque**   | 本会话内全部请求帧 `PAYLOAD` 按 `INDEX` 顺序拼接的字节流              |
| **响应 opaque**   | 本会话内全部响应帧 `PAYLOAD` 按 `INDEX` 顺序拼接的字节流              |
| **opaque**      | 传输层按字节透传的字节序列                                       |


**规范用语**


| 规范表述               | 含义                             |
| ------------------ | ------------------------------ |
| `FLAGS.MORE = 1/0` | 本方向是否还有后续片                     |
| `INDEX = i`        | 片序号（0 起，最大 127）                |
| `PAYLOAD` 为空       | `DATA` 仅含 1 B `FLAGS`，应用字节数为 0 |
| `len(PAYLOAD) = n` | `PAYLOAD` 字节数为 n（0～15）         |
| `N_req` / `N_rsp`  | 请求 / 响应 opaque 总字节数（**应用层定义**） |

## 4. 帧格式

### 4.1 字段布局

```text
偏移   长度   字段     说明
────────────────────────────────────────────────────────
 0      1    SOF      固定帧头 0x55
 1      1    LEN      从 DATA 到 CRC8（含）的字节总数
 2    0～16  DATA     载荷；业务帧 **至少 1 B**（`FLAGS`）
 2+n    1    CRC8     帧校验，算法见 §9
────────────────────────────────────────────────────────
```

记 `DATA` 长度为 `n`（`0 ≤ n ≤ 16`）：

- `LEN = 1 + n`；整帧长度 = `3 + n`（`PAYLOAD` 为空时最短 **4 B**；最长 **19 B**）

请求/响应由 **会话角色** 区分（§5）。

### 4.2 十六进制示例（传输层）

**探活**（`FLAGS=0x00`，`PAYLOAD` 为空；请求/响应 **hex 相同**，由 **会话角色** 区分）：

```text
55 02 00 df
```

探活 **= 空 opaque 请求↔响应会话**（`N=0`，一对）；响应帧为 `FLAGS=0x00`，`PAYLOAD` 为空。

### 4.3 线帧、通道与 opaque 映射

传输层在应用 opaque 外增加线帧封装；映射关系如下：

```text
应用 JSON（应用层）  ←──  opaque  ←──  多片 PAYLOAD 按 INDEX 拼接
                                      ↑
                              每片 DATA = FLAGS + PAYLOAD
                                      ↑
线帧 Frame = SOF + LEN + DATA + CRC8
```


| 层次          | 单元    | 组成                                     | 方向 / 通道                                   |
| ----------- | ----- | -------------------------------------- | ----------------------------------------- |
| **线帧**      | Frame | `SOF` + `LEN` + `DATA` + `CRC8`；≤ 19 B | 请求/响应由 **会话角色** 判定（§5） |
| **DATA**    | 片载荷   | `FLAGS`(1 B) + `PAYLOAD`(0～15 B)       | 同线帧方向                                     |
| **一对**      | Pair  | 1 请求帧 + 1 响应帧，`INDEX` 相同               | 逐对交互                                      |
| **opaque**  | 会话字节流 | 全部 `PAYLOAD` 按 `INDEX` 升序拼接            | 请求 opaque / 响应 opaque 独立                  |
| **应用 JSON** | 业务消息  | UTF-8 文本                               | 见 [应用层专版 §5](./近场20B二进制帧串口协议-v2.0-应用层.md) |



| 长度            | 计算                |
| ------------- | ----------------- |
| 单片 `PAYLOAD`  | 0～15 B            |
| 单侧 opaque `N` | `K = ⌈N/15⌉` 片    |
| 线帧 `DATA`     | 1～16 B（含 `FLAGS`） |

## 5. 帧方向与通道

线帧 **请求 / 响应** 由 **本会话的发起方 / 应答方角色** 判定，**不由** `DATA` hex 单独判定。

| 判定方式 | 规则 |
| --- | --- |
| **请求帧** | **发起方** 在本会话中发出的线帧 |
| **响应帧** | **应答方** 在本会话中发出的线帧 |

物理通道路径（GATT / UART 与请求帧、响应帧的对应）**仅见 §1.3**。

### 5.1 响应帧要求


| 要求              | 说明                                     |
| --------------- | -------------------------------------- |
| **每片请求帧必有响应帧**  | 同 `INDEX`；**500 ms** 内由 **应答方** 发出           |
| **允许空 PAYLOAD** | `DATA` 可仅含 `FLAGS`（整帧 **4 B**）         |
| **DATA**        | **必有 FLAGS**（单片亦带）；后跟 0～15 B `PAYLOAD` |


**探活响应帧**（最短，末片）：`INDEX=0`，`MORE=0`，`PAYLOAD` 为空：

```text
55 02 00 df
```

**空载荷中间片响应帧**（续收后续片，非探活）：`INDEX=0`，`MORE=1`，`PAYLOAD` 为空：

```text
55 02 80 53
```

### 5.2 链路与会话判定

| 判定   | 条件                                                  |
| ---- | --------------------------------------------------- |
| 链路可用 | 探活时收到 **空 opaque 响应帧**（`FLAGS.MORE=0`，`PAYLOAD` 为空） |
| 业务完成 | 末对请求/响应帧的 `FLAGS.MORE` **均为 0** 且 **INDEX 相同**      |

## 6. FLAGS 与分片

### 6.1 FLAGS 适用范围

请求帧与响应帧的 `DATA` **均必有 FLAGS**（单片亦带 FLAGS）。

### 6.2 FLAGS 编码

```text
FLAGS    1 B     分片控制
PAYLOAD  0～15 B  opaque 字节
```

约束：`1 + len(PAYLOAD) ≤ 16`。


| FLAGS 位       | 含义                                   |
| ------------- | ------------------------------------ |
| `bit7`        | **MORE**：`1` = 本方向后续还有片；`0` = 本方向末片  |
| `bit0`～`bit6` | **INDEX**：片序号，从 **0** 递增；成对请求/响应帧须相同 |


```text
FLAGS = (MORE << 7) | (INDEX & 0x7F)

示例：
  INDEX=0, MORE=1  →  0x80
  INDEX=0, MORE=0  →  0x00
  INDEX=3, MORE=0  →  0x03
```

### 6.3 对数估算（传输层）

单侧 opaque 长度 `N` 字节时，该侧至少需 `K = ⌈N / 15⌉` 片。

一次会话的总对数 **由双方 opaque 长度与应用层约定共同决定**；传输层只要求：

- `INDEX` 从 0 **连续递增**；
- 末对两侧 `FLAGS.MORE` 均为 0。


| `N`（B） | `K = ⌈N/15⌉`                |
| ------ | --------------------------- |
| 0      | 1（空 opaque，一对，`FLAGS=0x00`） |
| 15     | 1                           |
| 16     | 2                           |
| 45     | 3                           |
| 100    | 7                           |


### 6.4 会话对数估算（近场）

单侧 opaque `N` 字节时，该侧分片数 `K = ⌈N/15⌉`。

| 场景 | 对数下界 | 说明 |
| --- | --- | --- |
| **探活** | **1** | 双侧 opaque 均为空 |
| **写配置** | **`K_req`** | 请求侧发完即结束；末对响应侧带结果 JSON（见 [应用层 §7](./近场20B二进制帧串口协议-v2.0-应用层.md)） |
| **读配置** | **`≥ max(K_req, K_rsp)`**，常 **`K_req + K_rsp - 1`** | 请求发完后发起方可能发 **`PAYLOAD` 为空的请求帧** 续收响应（见 [应用层 §8](./近场20B二进制帧串口协议-v2.0-应用层.md)） |

传输层 **§7.3 示例 C** 与读配置一致：`N_req=42`（3 片）、`N_rsp=44`（3 片），共 **5 对**。

**opaque 缓冲建议**（固件侧静态分配）：单侧 **1～4 KB**；超长由应用层回 `code=1`（见应用层 §4）。

## 7. 逐对交互（核心）

### 7.1 片级规则

```text
for INDEX = 0, 1, 2, … :
    发起方  经「请求通路」发送请求帧（INDEX, FLAGS.MORE, PAYLOAD_req）
    应答方  须在 500 ms 内经「响应通路」回复响应帧（同一 INDEX, …)
    发起方  收到响应帧后，若本侧还有下一片请求帧，须在 ≤ 50 ms 内发送（INDEX+1）
    当末对完成后，请求侧与响应侧 FLAGS.MORE 均为 0 → 会话结束
```

| 规则              | 说明                                                      |
| --------------- | ------------------------------------------------------- |
| **每片请求帧必有响应帧**  | 须逐对发送；一片请求帧对应一片响应帧                                      |
| **INDEX 成对**    | 第 `i` 片请求帧只对应第 `i` 片响应帧                                 |
| **MORE 独立**     | 请求侧与响应侧各自表示本方向是否还有后续片                                   |
| **末对对齐**        | **末对** 请求帧与响应帧的 `FLAGS.MORE` **均为 0**（中间对可任一侧 `MORE=1`） |
| **PAYLOAD 可为空** | 任一侧任一片的 `PAYLOAD` 均可为空；由应用层解释含义                         |


### 7.2 双缓冲重组

一次业务会话须维护 **两条独立缓冲**：


| 缓冲       | 来源                              | 交付时机                     |
| -------- | ------------------------------- | ------------------------ |
| **请求缓冲** | 拼接各 `INDEX` 的 **请求帧** `PAYLOAD` | 末对双方 `FLAGS.MORE=0` 后交付应用层 |
| **响应缓冲** | 拼接各 `INDEX` 的 **响应帧** `PAYLOAD` | 末对双方 `FLAGS.MORE=0` 后交付应用层 |


```text
1. 每完成一对，分别追加本 INDEX 的请求帧 PAYLOAD 与响应帧 PAYLOAD
2. INDEX 须从 0 连续递增
3. 末对双方 FLAGS.MORE 均为 0 时，两条缓冲分别交付应用层
4. opaque 内容交付应用层解析
```


| 规则       | 说明                               |
| -------- | -------------------------------- |
| INDEX 上限 | **127**                          |
| 重复对      | 同 `INDEX` 已完成 → 忽略重复请求帧或重复回相同响应帧 |
| 长度       | 由应用层验长                           |


### 7.3 传输层分片示例

**示例 A**：请求 opaque `N_req = 45 B`，响应 opaque `N_rsp = 10 B`，共 3 对。

```text
INDEX=0:  请求  MORE=1  PAYLOAD 15 B   响应  MORE=1  PAYLOAD 空
INDEX=1:  请求  MORE=1  PAYLOAD 15 B   响应  MORE=1  PAYLOAD 空
INDEX=2:  请求  MORE=0  PAYLOAD 15 B   响应  MORE=0  PAYLOAD 10 B
```

重组后：请求缓冲 45 B；响应缓冲 10 B。

**示例 B**：请求 opaque `N_req = 20 B`，响应 opaque `N_rsp = 20 B`，共 2 对。

```text
INDEX=0:  请求  MORE=1  PAYLOAD 15 B   响应  MORE=1  PAYLOAD 15 B
INDEX=1:  请求  MORE=0  PAYLOAD  5 B   响应  MORE=0  PAYLOAD  5 B
```

**示例 C**：请求 opaque `N_req = 42 B`，响应 opaque `N_rsp = 44 B`，共 5 对。

```text
INDEX=0:  请求  MORE=1  PAYLOAD 15 B   响应  MORE=1  PAYLOAD 空
INDEX=1:  请求  MORE=1  PAYLOAD 15 B   响应  MORE=1  PAYLOAD 空
INDEX=2:  请求  MORE=0  PAYLOAD 12 B   响应  MORE=1  PAYLOAD 15 B
INDEX=3:  请求  MORE=1  PAYLOAD 空     响应  MORE=1  PAYLOAD 15 B
INDEX=4:  请求  MORE=0  PAYLOAD 空     响应  MORE=0  PAYLOAD 14 B
```

> 示例 C 为 **读配置** 典型形态（与 [应用层 §8](./近场20B二进制帧串口协议-v2.0-应用层.md) 一致）：`INDEX≥3` 的 **空请求帧** 用于续收响应片；**应答方仍须逐对回响应帧**。

### 7.4 探活（空 opaque 会话）

探活与业务共用 **逐对** 模型，区别仅为 **双侧 opaque 均为空**（`N_req = N_rsp = 0`）：


| 项       | 规定                                             |
| ------- | ---------------------------------------------- |
| 对数      | **1 对**                                        |
| `FLAGS` | `0x00`（`INDEX=0`，`MORE=0`）                     |
| `DATA`  | 仅 1 B `FLAGS`，`PAYLOAD` 为空（`LEN=2`，整帧 **4 B**） |
| 线格式     | 请求/响应 **hex 相同**；由 **会话角色** 区分（§5）          |
| 超时      | 与业务相同：**500 ms** 对超时（§8.2）                     |
| 串行      | 探活会话结束后方可发起下一业务会话                              |

## 8. 状态时序与超时

### 8.1 典型交互

```text
发起方                           应答方
 │  请求帧 (INDEX=0, 探活)          │
 │ ───────────────────────────────►│
 │  响应帧 (INDEX=0)                │
 │ ◄───────────────────────────────│
 │  请求帧 (INDEX=0, 业务)          │
 │ ───────────────────────────────►│
 │  响应帧 (INDEX=0)                │
 │ ◄───────────────────────────────│
 │  请求帧 (INDEX=1)                │
 │ ───────────────────────────────►│
 │  响应帧 (INDEX=1)                │
 │ ◄───────────────────────────────│
 │  … 直至末对 FLAGS.MORE=0         │
 │  重组请求 opaque + 响应 opaque   │
```

### 8.2 超时机制

对超时则会话失败；**发起方** 停止发送并上报，由应用层决定是否重新发起会话。


| 项          | 默认值         | 起算点                    | 义务方     | 说明                          |
| ---------- | ----------- | ---------------------- | ------- | --------------------------- |
| **对超时**    | **500 ms**  | 发起方发出请求帧(`INDEX=i`)    | **发起方** | 须在此时间内收到同 `INDEX` 的响应帧（含探活） |
| **对超时**    | **500 ms**  | 应答方 **收到**请求帧(`INDEX=i`) | **应答方** | 须在此时间内 **发出**同 `INDEX` 的响应帧 |
| **相邻发送间隔** | **≤ 50 ms** | 发起方收到响应帧(`INDEX=i`) 之后 | **发起方** | 发下一片请求帧(`INDEX=i+1`) 的上限    |
| **会话恢复**   | 由应用层发起      | —                      | **发起方** | 重新发起完整会话                    |


### 8.3 串行规则

须待当前会话完成（**末对**上请求帧与响应帧的 `FLAGS.MORE` **均为 0**，或已判定超时）后，发起方可发起下一业务会话（**探活与业务相同**）。

## 9. 校验算法（CRC-8/MAXIM）


| 项    | 值                            |
| ---- | ---------------------------- |
| 算法   | **CRC-8/MAXIM**              |
| 多项式  | `0x31`（反射 `0x8C`）            |
| 初值   | `0x00`                       |
| 覆盖范围 | **SOF** 至 **DATA** 末字节       |
| 验帧   | 对含 CRC8 整帧再算，结果为 `0x00` 表示通过 |


```c
uint8_t crc8_maxim(const uint8_t *data, size_t len) {
    uint8_t crc = 0x00;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int b = 0; b < 8; b++)
            crc = (crc & 1) ? (crc >> 1) ^ 0x8C : (crc >> 1);
    }
    return crc;
}
```

### 9.1 组帧与验帧

记 `data_len` = `DATA` 字节数（含 FLAGS），整帧长度 `frame_len = 2 + data_len + 1`（SOF+LEN+DATA+CRC）。

**组帧（任一方发线帧）**：

```c
// frame[0]=0x55, frame[1]=data_len+1, frame[2..]=DATA, frame[frame_len-1]=crc
uint8_t len_field = data_len + 1;
uint8_t crc = crc8_maxim(frame, 2 + data_len);  /* SOF..DATA 末字节 */
frame[2 + data_len] = crc;
```

**验帧（任一方收线帧）**：

```c
bool ok = (crc8_maxim(frame, frame_len) == 0);  /* 对含 CRC 的整帧再算 */
```

**探活手算**：`DATA={0x00}` → `LEN=2` → CRC 覆盖 `55 02 00` → `CRC=0xdf` → 整帧 `55 02 00 df`。

## 10. 固件实现要点

以下以 **UART 对端** 为例；本端担任 **发起方 / 应答方** 时，请求通路与响应通路的物理映射见 **§1.3**。

### 10.1 线帧收帧状态机（字节流，双方共用）

参考 App 侧 `Sbf20Parser` 实现：

```text
WAIT_SOF → WAIT_LEN → WAIT_BODY → CHECK_CRC → 交付会话层 → WAIT_SOF
```

| 状态 | 行为 |
| --- | --- |
| **WAIT_SOF** | 非 `0x55` 丢弃；见 `0x55` 进入 WAIT_LEN |
| **WAIT_LEN** | 读 `LEN`；`frame_len = LEN + 2`；**合法 LEN：2～17**（整帧 4～19 B） |
| **WAIT_BODY** | 收满 `frame_len` 字节 |
| **CHECK_CRC** | `crc8_maxim(frame, frame_len)==0` → 交付；否则 **丢弃**，不回响应 |
| **UART 半包** | **100 ms** 无新字节 → 复位到 WAIT_SOF |

`LEN` 非法时：复位；若当前字节为 `0x55` 则立即进入 WAIT_LEN（重同步）。

### 10.2 会话状态机（应答方）

本端担任应答方时：经 **请求通路** 收请求帧、经 **响应通路** 发响应帧（映射见 §1.3）。

```text
IDLE → PAIR(i) → [拼缓冲] → IDLE
```

| 状态 | 行为 |
| --- | --- |
| **IDLE** | 等待请求帧；收到后进入 `PAIR(INDEX)` |
| **PAIR(i)** | 解析 FLAGS；**500 ms 内** 经响应通路发出响应帧（同 `INDEX`）；追加 PAYLOAD 到对应缓冲 |
| **INDEX** | 须从 0 **连续**递增；跳号 → **丢弃会话**，回到 IDLE |
| **末对** | 双方 `FLAGS.MORE=0` → 交付应用层（见应用层 §7/§8 解析时机） |

### 10.3 异常处理（应答方）

| 情况 | 行为 |
| --- | --- |
| CRC 失败 | 丢弃该帧；**不** 经响应通路回发 |
| `INDEX` 与当前会话不一致 | 丢弃帧或复位会话 |
| `INDEX` 跳号 | 复位会话，回到 IDLE |
| 重复 `INDEX`（已完成） | 忽略请求，或 **重复回发** 上一片响应 |
| 杂字节 / BT24 密码 | 非 `0x55` 丢弃；等待 SOF 同步 |
| 写配置：请求侧 `MORE=0` | 可开始 `JSON.parse` 请求；末对须回写结果 JSON |
| 读配置：空请求帧续收 | 仍须回响应片（可为空或 JSON 续片） |

### 10.4 实现检查清单（应答方）

- [ ] UART **9600 8N1**，与 BT24 一致
- [ ] 收帧：`LEN` 2～17，CRC 失败丢弃
- [ ] 探活：收 `55 02 00 df` → 原样回发 `55 02 00 df`
- [ ] 每片请求 **500 ms** 内回响应，**INDEX 相同**
- [ ] 读会话支持 **空请求帧** 续收（§6.4、应用层 §8）
- [ ] 静态缓冲 **1～4 KB** / 侧
- [ ] 100 ms UART 半包复位

### 10.5 会话状态机（发起方，可选）

本端担任发起方时：经 **请求通路** 发请求帧、经 **响应通路** 收响应帧（映射见 §1.3）；逐对规则与 §7 相同（500 ms 对超时、≤50 ms 相邻发送）。opaque 语义由产品定义。

## 11. 边界用例


| 场景       | 期望                                                          |
| -------- | ----------------------------------------------------------- |
| 最短帧      | 探活或空 `PAYLOAD` 确认：`FLAGS` 仅 1 B，`MORE=0`，`LEN=2`，总长 **4 B** |
| 最长帧      | `DATA=16 B`，总长 **19 B**                                     |
| 单片业务     | 一对请求/响应帧，`FLAGS=0x00`                                       |
| 大 opaque | 约 `⌈N/15⌉` 对；UART 9600 下链路耗时随 N 增长                          |
| 对超时      | **500 ms** 内须收到响应帧                                          |
| 发送间隔     | 收响应帧后 **≤ 50 ms** 内发下一片请求帧（**发起方**）                         |
